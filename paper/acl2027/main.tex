\begin{abstract}
Accessibility needs often do not change the underlying digital goal; they change what information, support, or interface state is required for usable completion. Computer-use agents (CUAs) could reduce access barriers by completing GUI workflows on users' behalf, yet current benchmarks mainly measure nominal task completion and provide little evidence about whether agents can satisfy accessibility-related requirements. We introduce \bench, an executable Windows benchmark with 198 tasks informed by 17 documented functional support requirements derived from real-user evidence, accessibility research, standards and design guidance, and platform documentation across visual, hearing, motor, and cognitive scenarios. Each task is paired with automatic setup and task-specific end-state evaluation, and the required accessibility condition is built into what counts as task success rather than added as an optional tool-use constraint. This design distinguishes generic execution failure from the accessibility-conditioned case in which the nominal GUI goal is reached but the required access-supporting outcome is not. \section{Introduction}

More than 1.3 billion people---approximately one in six people worldwide---experience significant disability \citep{whodisability}. GUI agents have substantial potential to improve computer access for people with disabilities by perceiving interfaces and executing multi-step interactions on their behalf. Yet accessibility remains only lightly studied in computer-use agents, and existing general-purpose benchmarks largely evaluate a homogeneous notion of task completion.

Recent work suggests that the accessibility problem is not well captured by inventing a separate class of ``disabled-user tasks.'' A11y-CUA places sighted and blind/low-vision users on the same 60 everyday Windows tasks, showing that high-level goals can be shared even when accessible perception, control, and monitoring differ substantially \citep{a11ycua}. Complementarily, Kodandaram et al. study blind screen-reader users using a desktop CUA in naturalistic workflows; the resulting commands likewise center on familiar desktop activities such as document editing, spreadsheet operations, application configuration, and file management \citep{arewethereyet}. Importantly, the agent-side breakdowns they observe---grounding, planning, constraint tracking, state maintenance, and termination---are largely familiar CUA failure mechanisms rather than failures unique to blindness. What changes in an accessibility setting is the consequence of those failures: when interface state is harder to inspect or verify through a user's access modality, the same execution error can create a larger burden for monitoring, verification, recovery, and handoff. Consistent with this distinction, blind participants asked not only for end-to-end automation, but also for interface explanation, situated troubleshooting, recovery support, and user-controlled execution around consequential or difficult-to-verify actions \citep{arewethereyet}. These findings motivate a separation between the \emph{underlying activity}, the agent's \emph{generic execution reliability}, and the \emph{conditions for usable assistance}. Accessibility-oriented evaluation should therefore preserve ordinary user goals while testing whether execution leaves the information, support, and user-facing state needed for those goals to be usable.

To address this gap, we introduce \bench, an executable Windows benchmark with 198 tasks spanning visual, hearing, motor, and cognitive functional groups. We first synthesize recurring accessibility needs from accessibility research, user surveys and stories, standards and design guidance, and platform documentation; we then use the resulting need taxonomy as the systematic unit for constructing controlled, executable tasks. Rather than constructing disability-exclusive activities or requiring agents to imitate a prescribed assistive-technology trajectory, we instantiate documented needs within ordinary workflows and make the resulting access requirement part of the graded end state. This operationalizes one prerequisite for assistive collaboration: when a user delegates execution, the agent should leave a usable, access-supporting result rather than merely reach a nominal task endpoint.

Accessibility-oriented evaluation also requires distinguishing nominal task completion from completion of the accessibility-specific requirement. An agent may, for example, place the correct items in a shopping cart while failing to update a checklist used for memory support, or complete a workflow while leaving a required accessibility setting disabled. We therefore decompose task success, where applicable, into the ordinary \taskout and the accessibility-specific \accessreq, enabling direct measurement of cases in which an agent completes the nominal workflow but still fails to satisfy the user's need.

We evaluate five recent computer-use agents---Agent S3 \citep{agents3}, CoAct-1 \citep{coact1}, GTA1 \citep{gta1}, HiSA \citep{hisa}, and LocalLSTC \citep{locallstc}---on OSWorld, WindowsAgentArena, and \bench under matched 15- and 50-step budgets. \todo{Insert headline cross-benchmark result.} \todo{Insert result on the effect of longer interaction budgets.} Decomposed evaluation further shows \todo{insert TaskOutcome--AccessRequirement gap}, while controlling for task difficulty and operating time indicates that \todo{insert complexity-controlled result}. \section{Related Work}

\paragraph{General computer-use benchmarks.}
WebArena and VisualWebArena evaluate realistic web interaction \citep{webarena,visualwebarena}; OSWorld extends executable evaluation to desktop applications and operating-system settings \citep{osworld}; WindowsAgentArena and AndroidWorld provide scalable desktop and mobile environments \citep{waa,androidworld}. Spider2-V applies execution-based evaluation to professional data workflows \citep{spider2v}, while VideoGUI, VideoWebArena, and OmniGUI broaden multimodal GUI evaluation \citep{videogui,videowebarena,omnigui}. These benchmarks establish reproducible environments, automatic initialization, and end-state evaluation for general computer use. Their primary construct, however, is whether an agent completes the nominal GUI goal; heterogeneous access needs are not explicitly represented as task-level completion conditions. \bench retains the executable-benchmark methodology but changes the construct being measured: a documented access need may alter the information that must be acquired, the user-facing representation or support artifact that must be produced, or the accessibility/continuation state that must be established or preserved.

\paragraph{Accessibility-oriented CUA studies.}
A11y-CUA is the closest prior work on accessibility-conditioned computer use \citep{a11ycua}. It contributes a dataset of sighted and blind/low-vision users performing the same 60 everyday Windows tasks and compares human traces with CUAs under default and accessibility-related interaction conditions. This matched-task design is important for our framing: accessibility does not necessarily imply a different high-level task distribution; the same goals can impose different requirements on perception, control, feedback, and collaboration. A11y-CUA shows substantial performance degradation under keyboard-only and magnified conditions and reveals systematic differences between sighted, blind/low-vision, and agent interaction strategies. Its central object, however, is accessibility-conditioned interaction and trajectory behavior, with a primary emphasis on blind/low-vision users; it does not aim to construct a cross-need executable benchmark in which heterogeneous accessibility requirements systematically modify the graded end state.

Kodandaram et al. provide complementary ecological evidence through a three-week diary study of eight blind screen-reader users interacting with a desktop CUA across 12 applications \citep{arewethereyet}. Their 1,258 participant-issued commands span ordinary desktop activities such as document editing, spreadsheet operations, application configuration, presentation editing, and file management. Their replay evaluation identifies grounding, hidden-path discovery, planning, constraint-tracking, state-maintenance, and termination failures. These failure mechanisms are not, by themselves, specific to blind users; closely related weaknesses are central problems in general-purpose CUA research. The accessibility-specific contribution of the study is instead to show how such breakdowns intersect with nonvisual use and with users' ability to understand, verify, recover from, or take over an agent's actions. Participants therefore wanted CUAs not only to execute tasks autonomously, but also to explain unfamiliar interfaces, identify what changed, provide situated troubleshooting and recovery support, help users learn workflows, and preserve user control around consequential or difficult-to-verify actions \citep{arewethereyet}. This positions accessible CUA design as an interaction and handoff problem around general agent reliability, rather than requiring an entirely separate taxonomy of agent errors. Our benchmark addresses a complementary, deliberately narrower question: across documented visual, hearing, motor, and cognitive needs, does delegated execution terminate in a state that satisfies both the nominal task and the access-need-specific condition?

\subsection{Task Definition}

Following prior executable computer-use benchmarks \citep{osworld,waa}, we formalize agent interaction with the desktop environment as a partially observable Markov decision process (POMDP)
\begin{equation}
\mathcal{M}=(\mathcal{S},\mathcal{O},\mathcal{A},\mathcal{P}),
\end{equation}
where $\mathcal{S}$ is the desktop state space, $\mathcal{O}$ the observation space exposed by an agent's scaffold, $\mathcal{A}$ the permitted action space, and $\mathcal{P}(s_{t+1}\mid s_t,a_t)$ the environment transition dynamics. Given an observation $o_t\in\mathcal{O}$ of the current state $s_t$, the agent selects an action $a_t\in\mathcal{A}$ and transitions the environment to $s_{t+1}$. The interaction terminates when the agent declares completion or reaches the maximum step budget.

An accessibility-oriented task is defined as
\begin{equation}
\tau=(I,s_0,G,R),
\end{equation}
where $I$ is a natural-language instruction, $s_0$ the initialized desktop state, $G$ the nominal task goal, and $R$ an accessibility requirement induced by the user's accessibility need. Starting from $s_0$, the agent produces a terminal state $s_T$. We distinguish two conditions on this state: $E_{\mathrm{task}}^\tau(s_T)$ indicates whether $G$ is satisfied, and $E_{\mathrm{access}}^\tau(s_T)$ indicates whether $R$ is satisfied. For binary tasks,
\begin{equation}
E_{\mathrm{full}}^\tau(s_T)
=E_{\mathrm{task}}^\tau(s_T)\land E_{\mathrm{access}}^\tau(s_T).
\end{equation}
This formulation captures cases in which an agent completes the nominal GUI workflow while leaving the accessibility requirement unmet. It also separates \emph{failure mechanism} from \emph{accessibility consequence}: a generic grounding, planning, or state-tracking error may prevent the underlying task itself, whereas $E_{\mathrm{task}}=1$ and $E_{\mathrm{access}}=0$ isolates the more specific case in which ordinary task success still fails to produce the required accessible outcome. We therefore evaluate the resulting user-facing state rather than requiring agents to imitate the interaction strategy of a person with a disability. This distinction is deliberate: prior human data show that sighted and blind/low-vision users can pursue the same task goals through heterogeneous interaction strategies \citep{a11ycua}, while blind users may value CUA support that helps them understand, recover, or learn without fully delegating the task \citep{arewethereyet}. Although \bench evaluates delegated completion rather than mixed-initiative interaction itself, it specifies what must be true at handoff for usable completion or continuation, not how the agent must get there.

\subsection{Task Construction}

The central design principle of \bench is \emph{evidence-informed, need-driven task construction}. We first derive and ground the need taxonomy in external accessibility evidence; task synthesis then begins from a documented need, determines how that need changes a usable completion condition, and instantiates the requirement in a controlled everyday GUI workflow consistent with the observed user behaviors associated with that need. This separates evidence gathering from benchmark synthesis and prevents accessibility relevance from being assigned post hoc based on the presence of an assistive technology or a disability label. The construction pipeline is illustrated in Figure~\ref{fig:pipeline}.

\paragraph{A concrete construction example.}
Figure~\ref{fig:pipeline} traces one released task from need to evaluator. The starting construct is H1, which captures the need to obtain spoken information through text. We instantiate it as appointment management: a fixed recording states that a home-support assessment is scheduled for September 29, 2026 at 1:15 PM, and the user asks the agent to recover these facts with Chrome Live Caption and create a 45-minute Thunderbird event. Creating the exact event satisfies $E_{\mathrm{task}}$, but it does not satisfy $E_{\mathrm{access}}$ unless Live Caption remains enabled. The environment uploads the pinned MP3, prepares a fixed Thunderbird profile, and opens both applications. At termination, one evaluator inspects the caption setting and a second checks the structured event fields; \fullsuccess is their conjunction. Removing the H1 requirement would remove the caption state and its check without changing the calendar goal, so the example passes the counterfactual relevance test. Appendix~\ref{app:construction_examples} gives eight additional worked examples spanning all four functional groups and all eight non-CAPTCHA workflow categories.

\paragraph{Formative evidence review.}
Before task synthesis, we conducted a formative review of accessibility research, user surveys and stories, standards and design guidance, and platform documentation to identify recurring functional barriers and support needs \citep{w3cpeople,w3cstories,webaimsr,w3cauditory,w3cphysical}. We abstract these findings into a 17-need taxonomy at a consistent level of functional support requirement; for each need, Appendix~\ref{app:taxonomy} also records representative observed user behaviors/scenarios and their supporting evidence. Many high-level digital goals---such as communication, information seeking, scheduling, shopping, and service access---are shared across users. This is consistent with matched-task evidence from A11y-CUA and with the ordinary desktop activities that emerge from blind users' naturalistic CUA use \citep{a11ycua,arewethereyet}. Accessibility needs can instead change the information representation, interaction conditions, persistent support, or continuation state required for usable completion.

\paragraph{Functional coverage.}
We organize tasks into four top-level functional groups---visual, hearing, motor, and cognitive---as operational slices of barriers exercised by GUI interaction, rather than as an exhaustive diagnostic taxonomy. They correspond to limitations in acquiring visual information, acquiring auditory information, executing physical input actions, and processing or maintaining task-relevant information, respectively, and are consistent with common accessibility framings of sight, hearing, movement, and cognitive abilities \citep{w3cpeople}. A functional organization is preferable to diagnosis-based grouping for our purpose because the same diagnosis can produce heterogeneous interaction needs, while similar GUI barriers can arise across diagnoses. We additionally annotate broad functional subgroups for finer-grained analysis, but treat them only as secondary, potentially overlapping labels; their definitions and mappings are given in Appendix~\ref{app:taxonomy}.

\paragraph{Why construct from needs?}
After the formative review, the 17 need IDs serve as the lowest-level constructs used to generate tasks. Each describes a functional support requirement rather than a particular application, assistive technology, platform mechanism, or barrier scenario. For example, Sticky Keys and Filter Keys are realizations of keyboard interaction adaptation rather than separate peer-level needs, and mouse-button settings are realizations of adapted pointer control. Using needs as the construction unit provides systematic coverage, separates a user requirement from any single implementation, and gives a reproducible unit for task design and validation. Every released core task maps to at least one documented need, and that need must materially change at least one observable completion condition: the information to be acquired, the user-facing representation or support artifact to be produced, or the accessibility/continuation state to be established or preserved. The resulting taxonomy contains 5 visual, 4 hearing, 4 motor, and 4 cognitive need IDs; the full definitions and evidence sources are provided in Appendix~\ref{app:taxonomy}. We distinguish attention/distraction reduction from readability/comprehension simplification, while continuing to exclude generic planning burden, long horizons, arithmetic, or decision difficulty unless they induce an observable accessibility-support requirement.

\paragraph{Why these workflows?}
Need IDs describe \emph{why} a task is accessibility-oriented; workflow categories describe \emph{what everyday activity} is being performed. To obtain broad life-domain coverage without inventing disability-exclusive activities, we use the WHO ICF Activities and Participation component as a coverage guide rather than reproducing its hierarchy verbatim \citep{whoicf}. This choice also reflects empirical evidence that sighted and blind/low-vision users often pursue the same everyday computer goals \citep{a11ycua}, and that blind users naturally delegate familiar desktop work to CUAs \citep{arewethereyet}. We therefore consolidate relevant digital activities into eight benchmark-specific everyday workflow categories: \textit{communication}, \textit{information}, \textit{management}, \textit{mobility}, \textit{consumption}, \textit{service}, \textit{health}, and \textit{access}. These categories are orthogonal to user groups and need IDs: the same workflow can exercise different access needs, and the same need can appear in multiple workflows. Accessibility enters the benchmark through the required information, support artifact, or persistent state, rather than through a separate set of supposedly disability-specific activities. CAPTCHA is a particularly salient accessibility barrier for screen-reader users; in WebAIM's 2024 Screen Reader User Survey, it was rated the most problematic web accessibility item \citep{webaimsr}. We therefore include \textit{captcha} as a cross-cutting, deterministic verification-barrier stress test rather than treating it as either a need or an everyday-life domain. CAPTCHA instances are mapped to the underlying functional requirement exercised by the challenge---for example, V1 or V5 for non-visual access to a visual challenge and H1 for non-auditory access to an audio challenge. Crossing documented needs with everyday workflows reduces a one-to-one coupling between disability group, application, and task type, and allows later analysis to separate need-related effects from workflow-specific difficulty.

\paragraph{Construction procedure.}
For each task, annotators first select a documented need, then instantiate it in an everyday scenario consistent with the observed user behavior/context documented for that need and determine how the need changes the required outcome. They write a concise user instruction, instantiate the scenario in the Windows environment, and implement both the initial-state configuration and the executable end-state evaluator. Every requirement stated in the instruction is mapped to an observable final-state check. For example, a C3 memory-support task may require both a correct shopping-cart state and an updated persistent checklist; a hearing task may require recovered spoken facts in a non-auditory representation; and a motor task may require a requested keyboard-assistance state to remain enabled after the underlying workflow is completed.

We apply a task-level counterfactual relevance check during construction: \emph{if the accessibility-specific requirement were removed, would the required information, user-facing artifact, persistent state, or evaluator remain essentially unchanged?} If so, the task does not exhibit a sufficiently strong accessibility construct and is revised, reassigned, or removed. This criterion rules out ordinary GUI tasks augmented with arbitrary accessibility labels or unrelated toggles, while allowing ordinary life goals whose usable completion conditions genuinely change under a documented access need.

\paragraph{Manual annotation and cross-validation.}
All tasks were manually constructed by three annotators, each with at least undergraduate-level training in computer science. We conducted three rounds of cross-validation. Every task authored by one annotator was manually evaluated and checked by the other two annotators, who verified task feasibility, instruction clarity, task--need alignment, consistency with the documented need and its supporting evidence, reproducibility of the initial state, and correctness of the evaluator. Reviewers also executed the task manually and checked that valid solutions were accepted and plausible incorrect states were rejected. Identified issues were revised and re-checked before inclusion in the benchmark. Thus, every released task was authored by one annotator and independently examined by the other two.

Task construction and validation required approximately 600 person-hours in total, or about three person-hours per task: roughly two hours for task design and implementation and one hour for cross-validation and revision. Across the benchmark, annotators implemented \todo{N initialization configurations/functions} and \todo{N executable evaluation metrics}. This manual process follows the execution-based curation philosophy of prior computer-use benchmarks \citep{osworld}, while extending quality control to the accessibility construct itself through an evidence-grounded need taxonomy and the counterfactual relevance check.

\subsection{Environment and Execution}

To ensure that every run starts from the same $s_0$, we reset a preconfigured Windows environment and execute task-specific setup functions before the agent begins. Depending on the task, setup can place source files or media on the desktop, open an application or webpage, restore a cart or local database, prepare an email or calendar state, or set an accessibility feature to a known value. We build on the OSWorld/WindowsAgentArena execution stack \citep{osworld,waa} and use common Windows applications such as Edge/Chrome, Thunderbird Mail and Calendar, Sticky Notes, Notepad, LibreOffice, Windows Settings, and built-in accessibility features.

Some web tasks use self-hosted or pinned services when a live website would make the initial state or expected answer unstable. These include shopping, CMS, Wikipedia, forum, and CAPTCHA workflows. Hearing tasks use short pinned media or fixed task-specific audio when reproducibility requires it. The benchmark therefore preserves normal GUI interaction while keeping the state seen by different agents comparable across runs. Deployment details are provided in Appendix~\ref{app:implementation}.

\subsection{Evaluation}

After an agent stops, task-specific evaluators retrieve the state relevant to the instruction and compare it with the expected result. The evaluators take three broad forms: \textbf{structured-state checks} for settings, browser state, carts, calendar entries, mail fields, and spreadsheet cells; \textbf{artifact checks} for files, notes, or other saved outputs; and \textbf{content checks} for information recovered from text, images, or audio. Natural-language content is decomposed into required facts rather than matched as a single exact string, while fields such as dates, recipients, URLs, quantities, and settings are checked structurally whenever possible.

For reporting, we denote $E_{\mathrm{task}}$, $E_{\mathrm{access}}$, and $E_{\mathrm{full}}$ as \taskout, \accessreq, and \fullsuccess, respectively. On the subset $D$ where the nominal outcome and accessibility requirement are distinct, we additionally report
\begin{equation}
\mathrm{Gap}_D=P(E_{\mathrm{task}}=1,E_{\mathrm{access}}=0\mid D),
\end{equation}
\begin{equation}
\mathrm{CRS}_D=P(E_{\mathrm{access}}=1\mid E_{\mathrm{task}}=1,D).
\end{equation}
The first quantity measures how often an agent completes the underlying workflow but misses the accessibility requirement; the second measures how often the requirement is satisfied once the underlying task is complete. Coincident tasks, such as directly creating a requested reminder or enabling a requested accessibility setting, remain in the overall \taskout/\accessreq/\fullsuccess results but are excluded from the gap calculation. \section{Failure Analysis and Method Motivation}

Aggregate success rates show that agents struggle on \bench, but trajectory analysis must distinguish \emph{why the agent failed} from \emph{why that failure matters for accessibility}. We therefore annotate a stratified sample of failed runs with general execution mechanisms---including grounding and focus, task-state tracking, user-constraint loss, cross-application transfer, and completion verification---together with accessibility-facing consequences such as failure to acquire information in the required modality, failure to construct or update a persistent support artifact, and failure to preserve a required accessibility or continuation state. \todo{Insert sample size, annotator agreement, and failure distribution.} This separation avoids relabeling familiar CUA weaknesses as disability-specific simply because they occur in an accessibility-oriented task.

The failures often occur after the agent has already made substantial progress. Some agents never obtain the relevant visual or auditory evidence; others recover the right information but lose it when moving between applications, omit part of it from the final artifact, or stop without checking the requested state. \todo{Insert two or three representative failure patterns with frequencies.} The resulting requirement gap is therefore not necessarily caused by a new class of accessibility-specific reasoning error. Rather, generic reliability failures can propagate into accessibility-specific consequences at the point of representation, persistence, verification, or handoff. Reliable assistance consequently requires not only low-level GUI control, but also keeping the user's access requirement active throughout a long trajectory and verifying the requested condition before returning control. Prior interviews with blind users make this distinction especially salient: useful support may require state explanation, recovery, learning, and user-controlled execution because users need to understand and verify what the agent has done, not merely receive a nominal ``done'' signal \citep{arewethereyet}.

One baseline provides a concrete illustration. LocalLSTC--Qwen3.8-27B obtains 56.0\% full success on the 200 tasks, compared with 58.0\% nominal task success and 66.0\% access-requirement satisfaction. On the 51 tasks whose two components are separately observable, only 19 satisfy both: 20 satisfy the access requirement but not the nominal goal, four show the reverse pattern, and eight satisfy neither. Thus, for this system, the dominant decomposed failure is not simply forgetting to enable an accessibility feature. It often establishes the requested support state but fails to recover, transfer, or faithfully encode the task information needed downstream. Hearing tasks make this distinction especially visible: access-requirement satisfaction reaches 78.0\%, while full success is 50.0\%. Two scaffold limitations recur in the trajectories: the GUI grounder does not always localize the intended control accurately, and speech is observed only through intermittent screenshots of transient captions. Grounding errors are especially consequential for blind and low-vision users because an incorrect action may be difficult to notice, verify, or recover from without reliable nonvisual feedback. Appendix~\ref{app:locallstc_case} reports the complete case-study breakdown and attribution caveats.

\section{Conclusion}

We introduced \bench, a 198-task executable Windows benchmark for evaluating CUAs on everyday tasks shaped by diverse accessibility needs. The benchmark is built around a distinction supported by recent human-centered CUA studies: accessibility need not imply different high-level computer goals, and the underlying agent failures need not be unique to disabled users, while the conditions and consequences of usable assistance can differ substantially \citep{a11ycua,arewethereyet}. Accordingly, \bench does not seek a separate taxonomy of ``accessibility-specific agent errors.'' Instead, documented needs derived from real-user and accessibility evidence determine what information, support artifact, or continuation state must hold at the end of an otherwise ordinary workflow. Task-specific evaluators then separate nominal \taskout from \accessreq, making visible the cases where generic CUA execution reaches the ordinary goal but still leaves an access-incomplete terminal state. \section{Limitations}

\bench is not a complete model of disability or of how any individual person uses a computer. The four functional groups are analytical slices, and real users often have overlapping, changing, and highly individual needs. Although task construction is informed by published real-user and accessibility evidence, the benchmark tasks are controlled synthetic realizations rather than direct reproductions of participant-generated tasks; this evidence-informed construction does not replace participatory or large-scale validation with target users. The benchmark also evaluates delegated task completion and user-facing end states, not the full space of mixed-initiative assistance that users may want, such as interactive explanation, clarification, teaching, or shared control \citep{arewethereyet}. In particular, it does not directly measure trajectory-level observability, the effort required for a user to verify an agent's actions, or the quality of mid-task recovery and handoff after an error; our terminal-state checks capture only one prerequisite for such collaboration. The current benchmark is limited to Windows desktop interaction, and its application mix cannot represent every digital setting. Self-hosted services and fixed media improve reproducibility but remove some open-world variation. Difficulty and operating time depend on the final annotation protocol, and cross-benchmark comparisons are valid only when agent configurations and budgets are genuinely matched. Finally, deterministic evaluators may miss valid outcomes that were not anticipated during benchmark construction, and continuation-state checks measure whether future use remains possible rather than whether a user actually continues the workflow.

\section{Ethical Considerations}

The benchmark is intended to evaluate assistance, not to prescribe how people with disabilities should interact with technology or which accessibility features they should prefer. A platform feature's documented purpose does not imply that every user wants it enabled. Results for a functional group should not be interpreted as a prediction of capability for all people in that group. We also do not assume that successful assistance means maximal automation: users may prefer explanation, guidance, shared control, or confirmation while remaining engaged in the task \citep{arewethereyet}. In high-risk health, financial, identity, or other consequential workflows, user control and appropriate confirmation remain important even if an agent can technically complete the GUI task. \bench therefore should not be read as evidence that autonomous agents can replace user autonomy, accessibility expertise, or direct participation by people with disabilities in system design.

\section{Task Curation and Cross-Validation Details}

Three annotators with at least undergraduate-level training in computer science manually constructed the benchmark. Review covered feasibility, instruction clarity, task--need fit, consistency with the documented need and its supporting real-user/accessibility evidence, reproducibility of the setup, and evaluator correctness. The counterfactual relevance check asked whether removing the access-specific requirement would leave the required information, artifact, persistent state, or evaluator essentially unchanged; tasks failing this check were revised, reassigned, or removed. \subsection{Observation-channel limitation for transient captions}

The H1 failures expose a limitation of the observation interface as well as of the planner. The baseline does not receive a continuous caption transcript or an audio stream. It obtains screenshots at action and observation boundaries and must read whatever portion of the Live Caption overlay happens to be visible in those frames. Captions are transient: text may appear and disappear between two screenshots, a later utterance may overwrite an earlier one, and a single frame may contain only a suffix of the information needed for the task. Enabling Live Caption can therefore satisfy the measured access state while leaving the agent without a complete record of dates, codes, quantities, alternatives, or their order. No amount of reasoning over the observed frames can recover an utterance that was never captured.

This mechanism is visible in downstream artifacts. In \nolinkurl{communication-dental_reschedule_voicemail}, the system leaves Live Caption enabled and persists Thunderbird drafts, but its body omits required fields such as the weekday and year and normalizes the confirmation code incompletely; the run receives $A=1,T=0$. Other H1 runs similarly obtain the accessibility state but fail when converting transient speech into an email, note, calendar entry, CMS update, or factual answer. We therefore code these cases separately from failures in which the agent saw the relevant caption evidence but later lost or miscopied it. The former are observation-coverage failures induced by temporally sparse screenshot sampling; the latter are planning, memory, transfer, or artifact-construction failures.

This finding is specific to the evaluated scaffold rather than an unavoidable property of caption-based assistance. A continuous caption-event stream, transcript buffer, denser temporally triggered observations, or an explicit replay-and-accumulate policy could expose the missing evidence. The benchmark nevertheless reveals whether a deployed CUA's actual observation channel is adequate for speech-to-text tasks; merely toggling the platform feature is insufficient.

\subsection{GUI-grounding errors and accessibility consequences}

The GUI grounder does not always localize the intended control accurately. A mis-grounded click can activate a neighboring control, place focus in the wrong field, alter an unintended setting, or leave the interface unchanged while the agent assumes progress. Repeated attempts then consume the interaction budget and can propagate stale state into later actions. These are familiar GUI-agent failures, but their consequences are amplified in accessibility-oriented use. Blind and low-vision users may be unable to visually inspect the resulting screen, identify which control was activated, or independently reverse an unintended change. An apparently small grounding error can therefore increase the burden of verification, recovery, and handoff, and may leave the user in a less usable interface state than before delegation.

Trajectory coding treats incorrect target localization as a grounding failure and records its downstream consequence separately: nominal-task corruption, failure to preserve an accessibility setting, or loss of a usable continuation state. This separation avoids presenting grounding as unique to disability while capturing why the same error can be more costly when the user relies on the agent for nonvisual access or proxy interaction.

\subsection{Representative failure mechanisms}

The following patterns recur in the inspected trajectories.

\paragraph{Partial verification and false completion.}
The agent frequently verifies that an action produced some visible or file-level change without checking all task constraints. In \nolinkurl{captcha-hold_button_1}, the button changes to \emph{Complete} and the progress bar fills, after which the agent terminates; the evaluator requires navigation to the success URL, implying that an additional continuation action remains. In \nolinkurl{information-cat_image_alt_text}, the agent verifies only that a description attribute exists in the DOCX package. The saved description mentions a cat and car hood but omits task-relevant visual attributes required by the evaluator. These are general termination and constraint-coverage errors whose consequence is an incomplete accessible result.

\paragraph{Plausible inference after failed perception.}
When OCR or visual inspection remains ambiguous, the agent sometimes substitutes world knowledge or a locally plausible relation for evidence from the supplied artifact. In \nolinkurl{mobility-cta_airport_transfer}, it correctly identifies O'Hare, the Blue Line, Clark/Lake, and Midway, but writes Green Line rather than the required Orange Line. The trajectory explicitly records uncertainty in OCR before the model nonetheless describes its answer as verified. This mechanism is shared with ordinary visual benchmarks; the accessibility-specific consequence is that the generated textual route is intended to replace visual access to the map and must therefore be evidence-complete.

\paragraph{Persistent artifact updated despite an incorrect nominal result.}
In cognitive consumption tasks, the model can update a checklist or spreadsheet status while selecting the wrong item or variant in the web workflow. For example, \nolinkurl{consumption-lowest_price_white_mouse} changes the spreadsheet's Mouse status to \texttt{Done} and saves a product note, satisfying the persistent-memory component, but the cart does not contain the required product and option. The support artifact can therefore become confidently wrong, which is more consequential than simply omitting it because it may guide subsequent user action.

\paragraph{Exact assistive-state configuration.}
The model is more reliable at opening common accessibility features than at selecting exact variants or parameter values. It succeeds on opening Magnifier, Narrator, the on-screen keyboard, Mouse Keys, and Sticky Keys in several tasks, but fails on examples requiring 200\% magnification, a particular color-vision filter, ClickLock, Filter Keys, a specified audio-flash mode, or a swapped primary mouse button. These failures combine generic settings navigation with a benchmark-specific continuation-state requirement: the requested configuration must remain correct when control returns to the user.

\paragraph{Sustained and precision pointer interaction.}
Simple clicks and checkboxes are substantially easier than hold, slide, patch-selection, and other continuous or precision-dependent challenges. This is a generic control limitation, but the M4 tasks expose it specifically where the user delegated the interaction because sustained or precise pointer control is inaccessible. The benchmark therefore changes the practical interpretation of the same low-level failure: an unsuccessful proxy action leaves the original access barrier in place.

\subsection{Complex-PDF case: layout-aware visual verification}
\label{app:polisher_pdf_case}

Task \nolinkurl{consumption-cheapest_polisher} provides a representative case in which a document's text layer is useful for retrieval but unreliable for final semantic verification. The source is a 57-page, untagged Harbor Freight catalogue with dense multi-column product blocks, interleaved names, item numbers, sale prices, comparison prices, and promotional text. Its embedded text is therefore not read in the same two-dimensional order in which the page is visually organized. The complete released instruction is:

\begin{quote}
\small
\textbf{Instruction.} I have difficulty using a physical keyboard. Open the Windows On-Screen Keyboard and leave it available for me. Find the cheapest polisher in the provided Harbor Freight catalogue and save its full product name exactly as shown on the first line and its price on the second line of \texttt{answer.txt} on the Desktop.
\end{quote}

A text-only strategy repeatedly formed plausible but incorrect name--price associations. On physical PDF page~6, extraction placed \texttt{\$19.99} before the line \texttt{6" PALM POLISHER} and \texttt{\$109.99} after its item number, making nearest-line matching assign the wrong price. Page~13 contained the lexically cheaper \texttt{6 PIECE POLISHER ACCESSORY KIT} at \texttt{\$14.99}, although it is an accessory rather than a polisher. On page~17, a nearby \texttt{\$9.99} belonged to a cut-off tool, while the actual \texttt{3" POLISHER KIT} cost \texttt{\$34.99}. These errors are not resolved by extracting more neighboring lines because the missing relation is spatial: product names and prices occupy aligned visual blocks rather than a reliable linear text sequence.

The successful trajectory used the two PDF APIs as complementary channels. First, \texttt{PdfTools.extract\_text} stored the complete text with explicit physical-page markers. A keyword search reduced 57 pages to candidate pages 6, 13, and 17. Second, \texttt{PdfTools.render\_page} rendered each candidate page and returned the PNG directly as the first visual input to the planner, avoiding viewer chrome, viewport cropping, and desktop-resolution downsampling. The agent first identified the \texttt{\$19.99} palm polisher on page~6. It then inspected page~17 to reject the text-derived \texttt{\$9.99} hypothesis, inspected page~13 to classify the \texttt{\$14.99} result as an accessory kit, and finally re-rendered page~6 at 200~DPI to verify the exact output string. It wrote \texttt{6" PALM POLISHER} and \texttt{\$19.99} to \texttt{answer.txt}, left the On-Screen Keyboard open, and received full executable credit. Table~\ref{tab:polisher-disambiguation} summarizes the disambiguation, and Figure~\ref{fig:polisher-pdf-evidence} shows the rendered evidence supplied to the model.

\subsection{Implications for model and scaffold design}

The case study suggests four separable interventions. First, verification should maintain an explicit checklist for both $G$ and $R$ and inspect semantic field coverage rather than testing only whether a file, setting, or widget changed. Second, transient modalities require accumulation: caption events or repeated frame observations should be buffered into a persistent evidence record before downstream action. Third, GUI grounding should expose confidence and support verification through interface state rather than assuming that a generated click reached its intended target. Fourth, recovery should be hypothesis-driven and bounded; repeated attempts that do not generate new evidence should trigger a change of channel or a return to the last verified state. These interventions target both ordinary GUI reliability and the accessibility-conditioned points at which missing evidence or incomplete state becomes unusable assistance.

\section{Additional Task-Construction Examples}
\label{app:construction_examples}

The eight examples below complement the H1 management example in Figure~\ref{fig:pipeline}. We select two tasks per functional group and one task from each non-CAPTCHA workflow category. Every selected task received an A naturalness rating and a low runtime web-risk rating in our task audit. Each example reproduces the complete user-facing instruction from the released task JSON, then identifies how its setup and evaluator make the accessibility-oriented completion condition executable.

\subsection{Visual}

\paragraph{Mobility: finding the nearest pharmacy.}
Task \nolinkurl{mobility-nearest_pharmacy_marina_bay_sands} represents V1 non-visual access in a mobility workflow. \textbf{Instruction.} I rely on a screen reader to follow the content. Turn on Windows Narrator and use the provided walking-distance directory with Marina Bay Sands, Singapore as the current location. Choose the pharmacy with the shortest displayed walking distance, breaking a tie by the shorter walking time, then open that pharmacy's place details and leave them open. \textbf{Construction and evaluation.} Setup opens a fixed local HTML directory in Chrome with eight fully interactive, non-ranked candidates, avoiding dependence on a live map or directory. Two candidates share the shortest distance, so the walking-time tie-break is necessary. Full success requires both Narrator to remain enabled and the selected detail view to contain the correct pharmacy name, address, 0.4-km distance, and six-minute walking time.

\paragraph{Consumption: purchasing a catalogued product.}
Task \nolinkurl{consumption-lavender_coupon} exercises V1 in an online-shopping workflow. \textbf{Instruction.} I rely on a screen reader to shop online. Turn on Windows Narrator, then use OneStopShop to find the French Provence live lavender plant with blue flowers that comes as one plant in a 2.5-quart pot. Add exactly one unit to the shopping cart, enter coupon code \texttt{LAVENDER20} without applying it, and leave the cart page open. \textbf{Construction and evaluation.} Setup resets and opens the self-hosted storefront. Conjunctive checks require Narrator, the exact product and quantity, coupon code \texttt{LAVENDER20}, and the cart as the active page.

\subsection{Hearing}

\paragraph{Communication: responding to a dental voicemail.}
Task \nolinkurl{communication-dental_reschedule_voicemail} instantiates H1 text/non-auditory access to speech and H4 audio-channel adaptation in an email workflow. \textbf{Instruction.} I hear primarily through one ear and rely on captions for clarity. Turn on Mono audio, then use Chrome Live Caption to read the dental voicemail on the Desktop. Choose the earlier of the two offered appointments and create and save a Thunderbird draft to \texttt{appointments@example.com} with subject \texttt{Dental reschedule}, including the chosen date, time, and confirmation code. Do not send it. \textbf{Construction and evaluation.} Setup opens a fixed MP3 in Chrome and prepares Thunderbird. Accessibility evaluators require both Mono audio and Live Caption to remain enabled; the outcome evaluator checks the recipient, subject, and the four required body facts for the September 17 appointment.

\paragraph{Service: recording council pickup instructions.}
Task \nolinkurl{service-council_document_pickup_audio} applies H1 text/non-auditory access and H2 caption presentation to a public-service workflow. \textbf{Instruction.} I cannot reliably hear the recording and need larger captions. Use Windows Live captions with the caption style set to Large text to read the council service recording on the Desktop. Save the pickup location, collection hours, item to bring, and reference number to \texttt{answer.txt}, one item per line in that order. \textbf{Construction and evaluation.} A pinned local recording removes public-media drift. Accessibility evaluators require Windows Live captions to remain enabled with the Large text style; the outcome evaluator applies ordered, line-based content checks for Civic Service Centre counter 4, the collection hours, photo identification, and reference \texttt{PS-482}.

\subsection{Motor}

\paragraph{Access: enabling alternative pointer control.}
Task \nolinkurl{access-enable_mouse_keys} directly realizes M3 alternative/adapted pointer control. \textbf{Instruction.} Precise mouse control is difficult for me. Turn on Windows Mouse Keys and leave it enabled for me. \textbf{Construction and evaluation.} No external content or network setup is required. The evaluator reads the current user's Windows Mouse Keys flags and accepts only the enabled state, making the requested continuation state the graded result.

\paragraph{Health: preserving an alternative text-entry interface.}
Task \nolinkurl{health-insulin_storage_temperature} instantiates M1 in a health-information workflow. \textbf{Instruction.} I have difficulty using a physical keyboard. Open the Windows On-Screen Keyboard and leave it available for me. Save only the recommended refrigerated temperature range for unopened insulin from the provided insulin-storage PDF in \texttt{answer.txt} on the Desktop. \textbf{Construction and evaluation.} Setup opens a fixed local PDF in Chrome. Full success requires a visible On-Screen Keyboard process and an \texttt{answer.txt} file containing the accepted 36--46\,$^{\circ}$F range.

\subsection{Cognitive}

\paragraph{Management: creating a prospective-memory cue.}
Task \nolinkurl{management-prescription_refill_reminder} represents C4 time and prospective-memory support. \textbf{Instruction.} I rely on reminders and time cues to keep track of future actions. Create an all-day Thunderbird Calendar reminder titled \texttt{Refill medication} for the refill deadline in the pharmacy message on the Desktop. \textbf{Construction and evaluation.} Setup creates a fixed desktop message and prepares a Thunderbird profile. A structured calendar evaluator checks the title, July 20, 2026 date, all-day duration, and time fields. The nominal and accessibility outcomes coincide because the reminder itself is the requested support artifact.

\paragraph{Information: externalizing reference locations.}
Task \nolinkurl{information-chrome_reference_bookmarks} realizes C3 memory externalization in an information workflow. \textbf{Instruction.} I rely on persistent written records so I do not have to remember important details. Save the two already-open local Wikipedia reference pages \texttt{Accessibility} and \texttt{Computer accessibility} as persistent bookmarks on the Chrome bookmark bar so they can be reopened without having to remember or search for them again. \textbf{Construction and evaluation.} Setup opens two fixed Kiwix pages hosted inside the benchmark environment. The evaluator inspects Chrome's structured bookmark state and requires both exact local URLs on the bookmark bar.
