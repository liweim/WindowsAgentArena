\author{Anonymous ACL submission}

\begin{abstract}
GUI agents can execute everyday computer tasks on a user's behalf, but successful execution does not guarantee that the result can be used when control returns to the user. This distinction is consequential for people with accessibility needs: a task may be nominally complete while essential information is unavailable in an accessible representation, a memory-support artifact is stale, or an assistive interface has not been left usable. We argue that an \emph{accessibility-conditioned handoff} is a necessary (but not sufficient) condition for usable delegated assistance. Importantly, a user may need an assistive tool at handoff without requiring the agent to use that tool during execution; we therefore evaluate observable handoff conditions rather than prescribed agent trajectories. We introduce \bench, an executable Windows benchmark with 198 tasks organized under 14 ISO/IEC 29138-1-grounded user-need IDs, synthesized from 17 evidence-informed working needs across visual, hearing, motor, and cognitive scenarios. Each task specifies a digital goal and an automatically checked, need-conditioned handoff requirement; these components may coincide for direct support-configuration tasks. Across four completed Qwen3.8-27B configurations, mean handoff readiness is higher than mean nominal task completion, yet the decomposed outcomes include both nominally successful runs with failed handoff and support-ready runs with incorrect task results. These outcomes show what nominal-task-only evaluation can overlook and why handoff readiness must be assessed separately, not that handoff is uniformly harder than task execution. We implement a handoff-aware extension of LocalLSTC that derives fixed delivery conditions, addresses and verifies them sequentially, stores cross-condition facts, preserves completed conditions during later planning, and selects APIs for the active condition. On a controlled 60-task split, LocalLSTC2 improves mean full success from 56.7 to 63.3 while reducing average prompt tokens from 258.3k to 229.0k and steps from 25.4 to 18.8.


\end{abstract}

\section{Introduction}

More than 1.3 billion people---approximately one in six people worldwide---experience significant disability \citep{whodisability}. GUI agents may reduce barriers to digital activities by perceiving and manipulating interfaces on users' behalf. Yet completing a workflow and \emph{handing back a usable result} are not equivalent. An agent might schedule an appointment correctly while leaving captions unavailable for subsequent audio, fill a shopping cart while failing to update the user's memory-support checklist, or retrieve information while leaving it in a form the user cannot inspect. The nominal goal is reached in each case, but the conditions for independently using, checking, or continuing the result may not be.

We define an \emph{access need} as what a user requires to access information or interact with a digital system effectively. Access needs depend on the user and context: the same GUI task can involve different accessibility requirements for different users. We therefore design benchmark tasks around documented access needs, so that each task explicitly tests a requirement that matters for accessible completion or use.

This motivates our central claim: \textbf{for delegated assistance conditioned on a documented accessibility need, an appropriate handoff state is necessary for usable completion}. We use \emph{handoff} to mean the observable state of the environment and user-facing outputs when the agent stops and control returns to the user. A handoff condition specifies what information must be available, what support artifact must exist, or which accessibility/continuation capability must remain usable for the particular need. This is a \emph{necessary but not sufficient} condition: checking terminal state cannot establish that a particular person will understand, trust, verify, or successfully continue the workflow. Our benchmark measures only the portion of handoff readiness that can be defined and checked reproducibly.

Crucially, \textbf{the user's need for assistive technology does not imply that the agent must operate through that technology}. A person may need Live Caption to inspect later audio, Narrator to navigate after control is returned, an on-screen keyboard for input, or a reminder to externalize memory. An agent may nevertheless obtain evidence or navigate using any permitted channel. The correct requirement is to leave the requested user-facing support ready at handoff, not to force the agent to read captions, use a screen reader, or imitate a human access strategy. This distinction makes accessibility a condition on \emph{assistance outcomes}, rather than an artificial restriction on how an autonomous executor must act.

The distinction also explains how accessibility-oriented tasks relate to ordinary computer-use benchmarks and to different user groups. Prior matched-task evidence finds sighted and blind/low-vision users pursuing the same everyday Windows goals \citep{a11ycua}, while a naturalistic study of blind users interacting with a desktop agent documents familiar workflows alongside demands for explanation, recovery, verification, and user control \citep{arewethereyet}. Thus the underlying activity and many execution failures are not disability-specific. What changes is the \emph{handoff contract}: a hearing-related need may require a non-auditory record of speech or maintained captioning; a motor-related need may require alternative input to remain available; a cognitive need may require an accurate persistent reminder; a visual need may require accessible information or a working nonvisual interface. These are functional requirements, not claims that users within a group are homogeneous. Ordinary benchmarks may also involve handoff, but they typically do not make a \emph{need-conditioned handoff requirement} an independent, graded part of success.

We introduce \bench, an executable Windows benchmark comprising 198 everyday tasks across visual, hearing, motor, and cognitive functional groups. Using ISO/IEC 29138-1:2018 as the primary reference for the final taxonomy, we select 14 user accessibility need IDs relevant to GUI interaction \citep{iso29138}. A formative evidence review and 17 preliminary working needs informed this selection and their task realizations. Each task begins with a documented need, couples an everyday goal to an observable requirement derived from that need, and uses a counterfactual test: removing the need must materially change what is required for user-facing completion; for pure support-configuration tasks, removing the need may eliminate the task rather than preserve a separate underlying workflow. We evaluate the terminal state, not whether the agent followed a particular assistive-technology trajectory.

Our evaluation separates nominal \taskout ($T$), need-conditioned \accessreq ($H$; handoff readiness), and \fullsuccess ($F=T\land H$). The four completed configurations all obtain higher mean $H$ than $T$. This marginal ordering does not imply reliable handoff: the joint outcomes contain both $T=1,H=0$ and the more frequent $T=0,H=1$. The former shows that nominal success can conceal a failed handoff; the latter shows that preparing an assistive state or support artifact cannot substitute for completing the underlying work correctly. We compare GUI-agent frameworks with planning, memory, and termination-control mechanisms, and inspect where their joint task--handoff contract breaks: collecting evidence, transferring information, constructing support artifacts, preserving assistive state, and verifying readiness before termination. The trajectories further show omitted requirements, incorrect configurations, and states invalidated or lost during later actions. These observations motivate organizing execution around the complete set of user-facing delivery conditions rather than introducing a new taxonomy of supposedly disability-specific GUI errors.

Our contributions are (i) a need-grounded definition of accessible handoff as an observable completion condition independent of the agent's chosen tools; (ii) a 198-task executable benchmark and decomposed evaluation protocol distinguishing task execution from handoff readiness; (iii) an empirical analysis showing that task completion and handoff readiness fail in both directions despite existing planning, memory, and termination-control mechanisms; and (iv) an implemented execution strategy that exposes delivery conditions to goal decomposition, tool selection, cross-condition fact storage, preservation prompts, and condition-level verification.


\section{Related Work}

\paragraph{General computer-use benchmarks.}
WebArena and VisualWebArena evaluate realistic web interaction \citep{webarena,visualwebarena}; OSWorld and WindowsAgentArena extend executable evaluation to desktop applications and operating-system settings \citep{osworld,waa}; AndroidWorld provides mobile environments \citep{androidworld}. Spider2-V, VideoGUI, VideoWebArena, and OmniGUI broaden the scope to professional data and multimodal workflows \citep{spider2v,videogui,videowebarena,omnigui}. These benchmarks establish reproducible environments, automatic setup, and state-based or trajectory-based evaluation. However, their primary success criterion is whether the requested digital action was completed. Even when successful runs leave an artifact or final screen for the user, they do not systematically vary and independently evaluate \emph{accessibility-conditioned handoff contracts}. \bench holds on to executable evaluation while making those contracts explicit.

\paragraph{Accessibility-oriented GUI agent studies.}
A11y-CUA compares sighted and blind/low-vision participants performing the same 60 Windows tasks and contrasts their interactions with agent behavior under default and accessibility-related conditions \citep{a11ycua}. It shows that familiar goals can involve different interaction and monitoring requirements, and that accessibility-conditioned input and display constraints can challenge current agents. The distinction in our work is between \emph{how agents act} and \emph{what they must leave for the user}: a user's reliance on an assistive modality need not become a mandatory agent execution channel.

Kodandaram et al. document 1,258 commands by eight blind screen-reader users in a three-week study involving a desktop GUI agent \citep{arewethereyet}. Alongside ordinary editing, file management, and application configuration, participants sought explanations, situational troubleshooting, recovery, learning support, and user-controlled completion. The observed grounding, planning, constraint-tracking, state-maintenance, and termination errors largely overlap with general GUI-agent weaknesses. Their consequences, however, are amplified when the user cannot readily inspect or repair the resulting state. This evidence motivates our focus on the \emph{boundary between automated work and user continuation}. Our benchmark measures a concrete prerequisite of that boundary: whether the terminal information, artifact, or interface state meets a documented need.

The defining object is a \emph{need-conditioned handoff contract}, not the agent's use of a particular assistive feature. \subsection{Task Definition: Handoff as a Necessary Condition}

Following executable computer-use benchmarks \citep{osworld,waa}, we represent interaction with the desktop as a partially observable Markov decision process
\begin{equation}
\mathcal{M}=(\mathcal{S},\mathcal{O},\mathcal{A},\mathcal{P}),
\end{equation}
where $\mathcal{S}$ is the desktop state space, $\mathcal{O}$ the observation interface provided by an agent scaffold, $\mathcal{A}$ the allowed actions, and $\mathcal{P}$ the state transition dynamics. An agent receives observations, executes actions, and ends at state $s_T$ upon declaring completion or exhausting its action budget.

We define an accessibility-conditioned delegated task as
\begin{equation}
\tau=(I,s_0,G,H_u),
\end{equation}
where $I$ is the user instruction, $s_0$ the initial desktop state, $G$ the ordinary digital goal, and $H_u$ the \emph{handoff contract} derived from documented access need $u$. The access need describes a user requirement; the contract translates that need into observable properties of the environment and user-facing outputs that must hold when the agent returns control. It may require access to task-relevant information in an appropriate representation, a complete and persistent support artifact, or a usable accessibility/continuation state. Different needs can induce different $H_u$ for the same nominal goal $G$, and the same need may be realized by different contracts in different tasks. Thus, a need ID does not prescribe a particular assistive technology or agent execution strategy.

Let $T^\tau(s_T)=E_{\mathrm{task}}^\tau(s_T)$ test whether the nominal goal is met, and let $H^\tau(s_T)=E_{\mathrm{access}}^\tau(s_T)$ test the task's observable handoff contract. For binary tasks, full benchmark success is
\begin{equation}
F^\tau(s_T)=T^\tau(s_T)\land H^\tau(s_T).
\label{eq:handoff-full}
\end{equation}
The use of $H$ for the existing \accessreq score emphasizes its role: it tests \emph{handoff readiness}, not compliance with an agent-side tool prescription. For a need requiring handoff condition $H_u$, usable continuation logically requires that condition; satisfying it alone does not establish actual user comprehension, trust, or successful continuation. The benchmark therefore assesses an \emph{operational proxy for a necessary condition}, not a comprehensive measure of accessibility.

\paragraph{Tools for the user versus tools for the agent.}
If $H_u$ specifies that Live Caption, Narrator, Mouse Keys, or an on-screen keyboard remain usable, the requested feature is part of the \emph{user's handoff state}. It is not automatically a constraint on the agent's perceptual or control channel. An agent may extract a recording's contents through any allowed evidence source while still being required to leave captions enabled for the user. Likewise, the agent need not navigate using Narrator to leave a screen-reader-ready desktop. This separation prevents an arbitrary dependence between the needs of the intended beneficiary and the implementation choices of the autonomous executor. Explicitly source-specific tasks would need separate process-level evaluation and are not what the terminal-state requirement alone measures.

\paragraph{Ordinary tasks and independently checkable handoff.}
A general-purpose benchmark typically checks $T$ and may implicitly assume the final state is useful. Our task definition additionally states and checks a documented $H_u$. The nominal goal can itself be configuring user-facing support, in which case the two checks coincide. If $T=1,H=0$, the ordinary task is finished but the need-conditioned handoff is incomplete. If $T=0,H=1$, the support state is ready but the actual work is not finished. Both are necessary for $F=1$. In some tasks, such as creating the requested reminder or enabling an access setting, the nominal goal and support condition coincide; they remain valid benchmark tasks but are excluded from analyses requiring independently observable $T$ and $H$.

The criterion distinguishing \bench from ordinary tasks is thus \emph{not that control is handed back}---all delegated computer use may have a final state---but that a \emph{need-conditioned, independently specified and evaluated handoff requirement} changes what counts as successful assistance. For tasks with distinct components, a counterfactual without that need can retain $G$ while removing or altering $H_u$. This formulation supports systematic comparisons across functional groups and across different handoff mechanisms without conflating them with workflow choice, tool presence, or execution length.

\subsection{Task Construction}

The central design principle of \bench is \emph{evidence-informed, need-driven task construction}. The same nominal GUI task can involve different accessibility requirements depending on the user's access need. We therefore start with a documented need ID, determine the information, interaction capability, or support it requires in a specific user scenario, and express that requirement as an observable handoff condition $H_u$. We then pair it with an everyday digital goal $G$, instantiate the GUI workflow, and create executable checks for both components. This order makes the need central to task design and prevents an unrelated accessibility feature from being added to an otherwise generic task. The construction pipeline is illustrated in Figure~\ref{fig:pipeline}.

\paragraph{Taxonomy selection and evidence review.}
We use ISO/IEC 29138-1:2018 as the primary reference for selecting 14 user accessibility need IDs relevant to GUI interaction (3 visual, 4 hearing, 4 motor, and 3 cognitive) \citep{iso29138}. To inform this selection and its task realizations, we reviewed accessibility research, user surveys and stories, standards and design guidance, and platform documentation for recurring functional barriers and support needs \citep{w3cpeople,w3cstories,webaimsr,w3cauditory,w3cphysical}. The formative work initially produced 17 working support needs, which we mapped and consolidated against the ISO user-need identifiers to obtain the 14 release-level IDs. Appendix~\ref{app:taxonomy} records each selected ID, its ISO identifier and scope, representative task realizations, and the explicit mapping from the 17 working needs. The four functional groups and the selected subset are benchmark-defined; ISO does not prescribe them or the associated GUI tasks. Many high-level digital goals---such as communication, information seeking, scheduling, shopping, and service access---are shared across users. This is consistent with matched-task evidence from A11y-CUA and with the ordinary desktop activities that emerge from blind users' naturalistic GUI agent use \citep{a11ycua,arewethereyet}. Accessibility needs can instead change the information representation, interaction conditions, persistent support, or continuation state required for usable completion.

\paragraph{Functional coverage.}
We organize tasks into four top-level functional groups---visual, hearing, motor, and cognitive---as operational slices of barriers exercised by GUI interaction, rather than as an exhaustive diagnostic taxonomy. They correspond to limitations in acquiring visual information, acquiring auditory information, executing physical input actions, and processing or maintaining task-relevant information, respectively, and are consistent with common accessibility framings of sight, hearing, movement, and cognitive abilities \citep{w3cpeople}. A functional organization is preferable to diagnosis-based grouping for our purpose because the same diagnosis can produce heterogeneous interaction needs, while similar GUI barriers can arise across diagnoses. We additionally annotate nine broad functional subgroups for finer-grained analysis, using relevant codes from the World Health Organization's International Classification of Functioning, Disability and Health (ICF) as standardized descriptions of functional domains \citep{whoicf}. The nine subgroup labels and their combinations of ICF categories are benchmark-defined and potentially overlapping, not ICF-defined diagnoses or population strata; definitions and task-to-subgroup assignment guidance appear in Appendix~\ref{app:taxonomy}.

\paragraph{Why construct from needs?}
Need IDs describe what users require for effective access or interaction, while task goals describe the digital activities being delegated. Beginning with a documented need ensures that each task tests a meaningful accessibility requirement, rather than treating disability labels, assistive tools, or applications as needs themselves. For the final taxonomy and release metadata, each selected ID points to an ISO/IEC 29138-1 user need, with relevant ISO instances and supporting need identifiers identified explicitly (Appendix~\ref{app:taxonomy}). We merge magnification, contrast, and colour-independent presentation under ISO need 5-2-1, and merge short-term memory externalization and prospective-memory cues under ISO need 6-3-4. We retain distinct needs where the standard distinguishes cross-modal visual information (5-1-2), textual equivalents of non-text information (6-2-4), and modality-specific presentation adaptations. Sticky Keys, Filter Keys, Mouse Keys, and reminder applications are possible task realizations, not need definitions. Each core task must map to at least one documented need and an explicit, task-specific handoff contract. The need must materially change the information available to the user, a persistent support artifact, or the accessibility/continuation state preserved for handoff. This mapping does not restrict the information sources or interaction methods an agent may use. ISO needs 3-6 and 11-3 additionally motivate retention and uninterrupted availability of accessibility support at handoff; they are cross-cutting principles rather than separate V/H/M/C task-generation IDs. We exclude generic planning burden, long horizons, arithmetic, or decision difficulty unless they induce an observable accessibility-support requirement.

\paragraph{Why these workflows?}
Need IDs describe \emph{why} a task is accessibility-oriented; workflow categories describe \emph{what everyday activity} is being performed. To obtain broad life-domain coverage without inventing disability-exclusive activities, we use the WHO ICF Activities and Participation component as a coverage guide rather than reproducing its hierarchy verbatim \citep{whoicf}. This choice also reflects empirical evidence that sighted and blind/low-vision users often pursue the same everyday computer goals \citep{a11ycua}, and that blind users naturally delegate familiar desktop work to GUI agents \citep{arewethereyet}. We therefore consolidate relevant digital activities into eight benchmark-specific everyday workflow categories: \textit{communication}, \textit{information}, \textit{management}, \textit{mobility}, \textit{consumption}, \textit{service}, \textit{health}, and \textit{access}. These categories are orthogonal to user groups and need IDs: the same workflow can exercise different access needs, and the same need can appear in multiple workflows. Accessibility enters the benchmark through the required information, support artifact, or persistent state, rather than through a separate set of supposedly disability-specific activities. CAPTCHA is a particularly salient accessibility barrier for screen-reader users; in WebAIM's 2024 Screen Reader User Survey, it was rated the most problematic web accessibility item \citep{webaimsr}. We therefore include \textit{captcha} as a cross-cutting, deterministic verification-barrier stress test rather than treating it as either a need or an everyday-life domain. CAPTCHA instances are mapped to the underlying functional requirement exercised by the challenge---for example, V1 (cross-modal visual access) or V3 (text equivalents of non-text information) for a visual challenge and H1 (cross-modal audio access) for an audio challenge. Crossing documented needs with everyday workflows reduces a one-to-one coupling between disability group, application, and task type, and allows later analysis to separate need-related effects from workflow-specific difficulty.

\paragraph{Construction procedure.}
For each task, annotators (1) select a documented access need ID and a relevant user scenario, (2) specify the user-facing information or support required by that need, (3) turn it into an observable handoff condition, and (4) pair it with an everyday digital goal. They then write an instruction that distinguishes the desired result and handoff state from optional agent-side tool use, instantiate the workflow in Windows, and implement reproducible setup and executable checks for both components. Every outcome requirement stated in the instruction must map to an observable final-state check. For example, a C3 memory-support task may require both a correct shopping-cart state and an updated persistent checklist; a hearing task may require recovered spoken facts in a non-auditory representation; and a motor task may require a requested keyboard-assistance state to remain enabled after the underlying workflow is completed.

We apply a task-level counterfactual relevance check during construction: \emph{if this user need were absent but the everyday goal remained, would the required handoff information, artifact, continuation capability, or evaluator materially change?} If neither the handoff requirement nor the meaningfulness of a support-only task changes, the task is revised, reassigned, or removed. A second alignment check asks whether the proposed handoff state supports this user's post-agent verification, use, or continuation of the particular workflow rather than merely adding an unrelated accessibility toggle. This guards against artificial requirements while retaining legitimate cases where an accessibility feature is requested for continued use after the agent finishes. \todo{Document per-task handoff alignment audit and revise any instances where the required support state is unrelated to the workflow.}

\paragraph{Manual annotation and cross-validation.}
All tasks were manually constructed by three annotators, each with at least undergraduate-level training in computer science. We conducted three rounds of cross-validation. Every task authored by one annotator was manually evaluated and checked by the other two annotators, who verified task feasibility, instruction clarity, task--need alignment, consistency with the documented need and its supporting evidence, reproducibility of the initial state, and correctness of the evaluator. Reviewers also executed the task manually and checked that valid solutions were accepted and plausible incorrect states were rejected. Identified issues were revised and re-checked before inclusion in the benchmark. Thus, every released task was authored by one annotator and independently examined by the other two.

Task construction and validation required approximately 600 person-hours in total, or about three person-hours per task: roughly two hours for task design and implementation and one hour for cross-validation and revision. Across the benchmark, annotators implemented \todo{N initialization configurations/functions} and \todo{N executable evaluation metrics}. This manual process follows the execution-based curation philosophy of prior computer-use benchmarks \citep{osworld}, while extending quality control to the accessibility construct itself through an evidence-grounded need taxonomy and the counterfactual relevance check.

\subsection{Environment and Execution}

To ensure a comparable handoff contract can be evaluated from the same initial state $s_0$, we reset a preconfigured Windows environment and execute task-specific setup functions before the agent begins. Depending on the task, setup can place source files or media on the desktop, open an application or webpage, restore a cart or local database, prepare an email or calendar state, or set an accessibility feature to a known value. We build on the OSWorld/WindowsAgentArena execution stack \citep{osworld,waa} and use common Windows applications such as Edge/Chrome, Thunderbird Mail and Calendar, Sticky Notes, Notepad, LibreOffice, Windows Settings, and built-in accessibility features.

Some web tasks use self-hosted or pinned services when a live website would make the initial state or expected answer unstable. These include shopping, CMS, Wikipedia, forum, and CAPTCHA workflows. Hearing tasks use short pinned media or fixed task-specific audio when reproducibility requires it. The benchmark therefore preserves normal GUI interaction while keeping the state seen by different agents comparable across runs. Deployment details are provided in Appendix~\ref{app:implementation}.

\subsection{Evaluation}

Task-specific evaluators inspect the desktop when the agent returns control. They check (i) the nominal workflow result and (ii) the observable part of the task's need-conditioned handoff contract. The underlying evaluators comprise \textbf{structured-state checks} for settings, carts, calendar entries, mail fields, and spreadsheet cells; \textbf{artifact checks} for notes, files, checklists, and bookmarks; and \textbf{content checks} for task-relevant facts recovered from text, images, or audio. Where appropriate, natural-language output is checked for required facts, while dates, quantities, URLs, application state, and other exact values are checked structurally.

We retain the existing score names for compatibility with task metadata but clarify their interpretation: \taskout is $T=E_{\mathrm{task}}$; \accessreq is $H=E_{\mathrm{access}}$, the task-specific \emph{handoff-readiness check}; and \fullsuccess is $F=T\land H$ (Eq.~\ref{eq:handoff-full}). \textbf{Assistive-tool usage by the agent is not a metric}: enabling and preserving a tool for the user may be graded as $H$, but acting through that tool is not required unless a task explicitly evaluates the process, which this benchmark does not.

For the subset $D$ of tasks where $T$ and $H$ are independently observable, we report
\begin{equation}
\mathrm{HandoffGap}_D=P(T=1,H=0\mid D),
\label{eq:handoff-gap}
\end{equation}
\begin{equation}
\mathrm{HandoffGivenTask}_D=P(H=1\mid T=1,D).
\label{eq:handoff-conditional}
\end{equation}
The first is the joint frequency of an ordinary-task success with an unmet handoff condition (corresponding to the previous \argap); the second is the fraction of nominally completed tasks that are handoff-ready (the previous \condsat). These denominators must not be conflated: in general, $\mathrm{HandoffGap}_D \neq 1-\mathrm{HandoffGivenTask}_D$. We also distinguish $T=0,H=1$, in which user-facing support is correctly established but the underlying task remains incomplete. Coincident tasks---such as directly enabling Mouse Keys or creating a requested reminder---are included in overall $T/H/F$ but excluded from independent-component gap statistics. We separately test the validity of natural-language evaluators using paraphrases, omitted facts, near misses, negations, and format variants. \todo{Insert validation outcomes and denominator sizes.}

The evaluators thus operationalize a \emph{necessary terminal condition}: a setting flag, saved artifact, or structured content check is evidence of a handoff-ready state under the benchmark contract, not proof that a specific user can actually perceive, understand, or continue successfully. Mid-task communication, quality of explanations, and recovery under shared control remain outside the current measured construct.

\section{Handoff-Centered Failure Analysis}
\label{sec:handoff-failures}

Our failure analysis asks \emph{where the transfer from agent execution to user-usable state breaks}. We distinguish the generic action-level mechanism (e.g., imprecise grounding, loss of constraints, weak state tracking, brittle cross-application navigation, or premature termination) from the \emph{handoff obligation} it violates. This avoids presenting familiar GUI failures as if they were mechanisms unique to particular disabilities. We organize the result records and inspected trajectories by the following handoff stages: (i) acquisition and preservation of task evidence; (ii) transfer of evidence across applications or modalities; (iii) accurate creation or updating of persistent user-facing artifacts; (iv) establishment and preservation of required assistive/continuation state; and (v) final verification and honest termination. Appendix~\ref{app:failure} gives the coding rule and distinguishes this audit synthesis from a formal multi-annotator study.

Across the current 198-task runs of Agent S3, CoAct, LocalLSTC, and HISA without pattern memory, all using Qwen3.8-27B, 464 of 792 terminal \texttt{result.txt} records are failures or partial failures under the strict criterion $F<1$. Of these runs, 361 (77.8\%) have $H=0$. The decomposition is important: 25 runs have $T=1,H=0$, so an ordinary task-success measure would conceal a failed accessibility-conditioned handoff, whereas 81 have $T=0,H=1$, meaning that support is present but the underlying work is wrong. The remaining 336 have $T=H=0$. This audit follows the failure definition \texttt{eval(result.txt) < 1}; Table~\ref{tab:main-accessneed} instead reports arithmetic mean scores at the fixed 50-step snapshot. For CoAct, the terminal and 50-step summaries differ, so their values must not be interchanged. The pooled audit counts are descriptive because the configurations share tasks, a model family, and parts of the environment.

\paragraph{Evidence does not survive to handoff.}
An agent may observe task-relevant speech or visual content yet fail to preserve the full evidence needed in a saved artifact or downstream application. H1, which requires audio information in another modality, fails in 28/44 Agent S3 runs, 39/44 CoAct runs, 23/44 LocalLSTC runs, and 30/44 HISA runs. A concrete observation-channel limitation appears in LocalLSTC: speech is sampled through intermittent screenshots of transient captions rather than a continuous transcript. A date, code, quantity, or negation can appear between observations or be overwritten, while a later fluent artifact hides the omission. Maps, images, and complex PDFs exhibit a related representation problem: linear OCR can destroy spatial relations, after which the agent sometimes presents a plausible inference as verified fact. The accessibility consequence is an incomplete or unreliable alternative representation.

\paragraph{The handoff artifact is plausible but wrong.}
The agent may create a reminder, checklist, note, or spreadsheet update while making an incorrect nominal decision in the underlying workflow. Conversely, it may finish the workflow while leaving the support artifact stale. Four hearing tasks produce $T=0,H=1$ under all four methods: \nolinkurl{health-long_covid_care_note}, \nolinkurl{information-ftc_washington_q4_fraud}, \nolinkurl{management-home_delivery_window_audio}, and \nolinkurl{service-cms_update_access_desk_page_audio}. The timer task \nolinkurl{management-quick_sponge_timer} produces the central $T=1,H=0$ handoff gap under all four. Neither direction is captured by an undifferentiated ``task completed'' message. Task facts and the downstream artifact or continuation state must therefore be tracked and checked separately.

\paragraph{The user-facing interface is not ready.}
A standard GUI grounding or settings-navigation error may leave a requested caption mode, on-screen keyboard, Mouse Keys configuration, magnification value, or screen reader inactive or incorrectly configured. Exact settings and delegated precision interaction are especially unstable. For M2, which includes timing and keyboard-control requirements, failure rates are 68.8\%, 81.2\%, 62.5\%, and 93.8\% for Agent S3, CoAct, LocalLSTC, and HISA; for M4 sustained or precise pointer interaction, they are 57.1\%, 71.4\%, 71.4\%, and 57.1\%. The underlying grounding and actuation errors are generic, but the accessibility consequence is direct: the requested continuation state is unusable, or the interaction barrier that motivated delegation remains. This does not imply that the agent must use the assistive feature itself; it requires independent verification of the state left for the user.

\paragraph{Premature termination breaks the handoff contract.}
Agents often stop after observing a local change, before rechecking the complete task, saved artifact, assistive state, or final view. Agent S3, CoAct, LocalLSTC, and HISA respectively self-report completion in 56, 52, 52, and 73 failed runs; 47, 47, 43, and 63 of those runs also have $H=0$. Long trajectories form a second general cluster: agents repeat ineffective clicks or scrolling, lose constraints across applications, exhaust the action budget, or leave too few steps for saving and verification. A pre-handoff audit should verify $G$ and $H_u$ separately and trigger bounded repair or an explicit incomplete-state report instead of an unqualified completion claim.

The overlap across methods indicates stable difficulty rather than one scaffold-specific defect. Fifty of 198 tasks fail under all four configurations, including 17 hearing, 16 visual, 9 motor, and 8 cognitive tasks; 33 tasks have $H=0$ for all four. Consumption accounts for 14 of the 50 common failures, followed by information (9), and communication, health, and mobility (5 each). Other recurring generic causes are imprecise grounding, incomplete conjunctive constraint tracking, cross-application transfer and save errors, and unsupported inference under uncertain perception. Appendix~\ref{app:failure} reports the complete decomposition, need and workflow slices, common-task set, and method-specific exceptions.

\section{Handoff-Aware Execution and Verification}
\label{sec:handoff-method}

The failure analysis shows that need-conditioned handoff requirements can be omitted or left unverified even when nominal work is completed, while a prepared support state can coexist with an incorrect task result. Motivated by these observed delivery failures, we extend LocalLSTC with a single organizing principle: \emph{preserve the complete set of user-facing delivery conditions while focusing each decision on the condition currently being completed}. This is an execution strategy for requirements already specified in the task, not a separate optimization objective. The implementation does not require an explicit $T/H$ type label. Instead, it derives all requested final deliverables and states from the instruction, including ordinary task results and need-conditioned handoff requirements, and keeps them connected to tool selection, retained facts, and completion checks.

\paragraph{Fixed completion conditions.}
At task start, the agent generates a short ordered list of immutable final verification goals. Requirements concerning one artifact or application state, including its contents, exact values, format, and saved status, remain in one condition rather than being split into action-level steps. Intermediate discoveries and tool calls are excluded. This list provides a stable terminal reference that LocalLSTC's dynamically proposed subgoals do not provide: the planner can focus on one operational stage without losing the remaining delivery requirements.

\paragraph{Condition-wise execution with preservation constraints.}
The agent addresses the fixed conditions sequentially. The active condition is exposed as the current verification goal, while previously verified conditions are supplied to the planner as constraints that later actions must preserve. After each action, step abstraction summarizes the current outcome and additionally checks whether the action changed any previously verified condition; if so, it explicitly names every affected condition and how it changed. When a condition finishes, the planner starts the next one with fresh local execution context. Exact information that remains necessary across conditions, such as dates, codes, paths, identifiers, quantities, and requested wording, is stored in a persistent global-fact map and re-injected after the local context reset. This combination keeps delivery constraints and task-critical facts available across condition boundaries.

\paragraph{Condition-aware API selection.}
Before each planner decision, JEV API evaluates the software-level methods available for the task's applications against the active condition, completed conditions, persistent facts, current application state, execution history, and recovery feedback. Only selected method descriptions are placed in the planner prompt; GUI and execution-side automation remain available, and failures in the selector fall back to the full API prompt. This component turns the current delivery condition into a concrete action-selection bias rather than treating condition tracking as passive bookkeeping. PDF methods are always retained because the implementation uses text extraction and rendered-page inspection as complementary evidence channels.

\paragraph{Condition-level verification and repair.}
When the planner requests termination of the active condition, a separate verifier evaluates that condition from its execution evidence and the latest screenshot. For persistent background state that is not visible, it requires a recent exact readback rather than accepting that an action merely ran. A failed judgment returns a specific finding to the planner and keeps the condition active for repair; a passed judgment records the condition as completed before execution advances. Previously completed conditions remain in the planner context as preservation constraints throughout later subtasks.

\paragraph{Supporting information channels.}
Audio transcription and PDF text/rendering APIs supply evidence that can be retained and used to build the requested result. They are enabling perception channels rather than the core handoff-aware mechanism: an internal transcript, extracted text, or global fact is not itself a user-facing handoff result. The agent must still create and verify the requested artifact or continuation state. JEV-based episodic-memory filtering is likewise an optional context-efficiency optimization; because its current ablation does not improve success, we report it separately in Appendix~\ref{app:method-ablation} rather than treating it as a primary method contribution.

\section{Conclusion}

We introduced \bench, an executable 198-task Windows benchmark that makes \emph{handoff readiness} an explicit necessary condition for delegated GUI assistance under documented accessibility needs. The framework separates the ordinary goal from the user-facing information, durable support, and continuation interface that must remain usable after the agent stops. This distinction explains why an assistive tool may be required \emph{for the user at handoff} without being required \emph{as an agent execution channel}, and why different accessibility needs can change task success without changing the underlying everyday activity.

Our decomposed evaluation distinguishes task completion $T$, need-conditioned handoff readiness $H$, and full success $F=T\land H$. In particular, $T=1,H=0$ isolates the gap that ordinary task-success metrics can overlook, while the more frequent $T=0,H=1$ outcome reveals apparently prepared but factually incorrect support. The fact that marginal $H$ exceeds $T$ for all four completed baselines reinforces the value of separately evaluating these requirements rather than assuming one score characterizes both. Trajectory analysis records omitted, misconfigured, and subsequently invalidated handoff conditions alongside incorrect nominal work. Motivated by these observations, LocalLSTC2 exposes specified delivery conditions to sequential execution, persistent facts, condition-aware API selection, preservation constraints, and condition-level verification. On the controlled 60-task split, it improves full success while reducing prompt tokens and interaction steps. Together, the benchmark and method make observable handoff prerequisites an explicit part of evaluating and supporting accessible GUI assistance.


\section{Limitations}

Our handoff construct is intentionally narrower than accessible user experience. A correct saved note, checked setting flag, or final application view can be a necessary prerequisite for usability without proving that a particular user can find, interpret, verify, trust, or continue from it. The benchmark does not directly score interactive clarification, explanations, shared control, user consent, mid-task recovery, or the effort required for verification after handoff. A setting may also be enabled but fail to function in a particular environment or with a particular combination of assistive tools. Terminal-state evaluators necessarily approximate these richer outcomes.

The four functional groups and 14 documented needs are analytical categories, not complete descriptions of any individual or diagnosis. Users may have overlapping and changing needs and distinct preferences, so the contract appropriate for one user is not universally appropriate for another. Tasks are controlled, evidence-informed synthetic realizations, not participant-generated workflows; external user validation is still needed, particularly for whether each handoff contract is meaningful in context. Requiring an assistive feature without a plausible link to the subsequent workflow would compromise construct validity; we therefore specify an alignment audit and flag instruction/evaluator mismatches for correction. In particular, examples whose recorded wording says that the agent must \emph{use} a specific assistive feature need to be reconciled with source-agnostic, end-state scoring. More broadly, a need-conditioned toggle that serves no plausible subsequent inspection or continuation purpose is not a valid handoff contract merely because it can be checked automatically.

The environment is limited to Windows and a fixed application mix, with self-hosted services and pinned media for reproducibility. Handoff content and tool states can be task-dependent, and deterministic evaluators may miss valid alternatives or user-facing defects outside their checks. The cross-method analysis covers four Qwen3.8-27B configurations on the same 198 tasks (792 configuration--task observations), while the current LocalLSTC2 evaluation uses a 60-task split. These repeated observations are not independent samples, and HISA is evaluated without pattern memory. Broader model and benchmark generalization, repeated-run uncertainty estimates, and individual ablations of fixed conditions, global facts, preservation constraints, and verification remain future work.


\section{Ethical Considerations}

A handoff contract should reflect a user's stated access needs and preferences, not prescribe universal behavior for a disability category. Leaving a feature enabled is appropriate only if the user requests or requires it in the particular setting; unwanted changes to accessibility configurations can themselves create access barriers. Likewise, source-agnostic agent execution does not justify hiding uncertainty or overriding user choice. Assistive technology supports user agency and continuation, rather than obliging the user to hand over tasks to an autonomous agent. The benchmark is an evaluation tool, not evidence that assistive tools or participatory design can be replaced by automation.

Especially in health, financial, identity, and other consequential workflows, agent actions may require informed confirmation, transparent records, and a safe opportunity to interrupt or correct the process. Our end-state checks do not replace those safeguards. Group-level results should not be interpreted as estimates of individual capabilities or preferences, and future studies should involve users with relevant lived experience in validating handoff contracts and evaluation procedures.

\paragraph{Legacy ID crosswalk and handoff.}
The final 14-label scheme consolidates the 17 formative working labels as follows: previous \texttt{V1}$\rightarrow$\texttt{V1}; \texttt{V2/V3/V4}$\rightarrow$\texttt{V2}; \texttt{V5}$\rightarrow$\texttt{V3}; \texttt{H1--H4}$\rightarrow$the corresponding \texttt{H1--H4}; \texttt{M1--M4}$\rightarrow$the corresponding \texttt{M1--M4}; \texttt{C1/C2}$\rightarrow$\texttt{C1/C2}; and \texttt{C3/C4}$\rightarrow$\texttt{C3}. Since ISO need IDs concern users and systems rather than agents, selecting a need does not mandate a particular agent sensing or actuation trajectory. ISO \textbf{3-6} (retaining individualization settings) and \textbf{11-3} (availability of accessibility functions without disruption) provide cross-cutting support for end-state handoff checks, without being counted as additional functional need IDs \citep{iso29138}. Need-level counts, ICF-informed subgroup assignments, and need-conditioned rates must be recomputed using the merged labels and scenario-specific subgroup assignment; existing task instances and evaluators are not changed by this relabeling. The task JSON and plots need the same mapping before these figures can be reported as final.

Each task has exactly one benchmark \texttt{user\_group} (visual, hearing, motor, or cognitive) and one or more \texttt{need\_ids}. The \texttt{need\_id\_to\_subgroup\_ids} crosswalk specifies \emph{eligible candidate subgroups}, not labels assigned automatically to every task with a given need. Annotators select only subgroup IDs warranted by the concrete scenario and observable user-facing accessibility requirement; multiple IDs are allowed where more than one subgroup is actually addressed. For example, a C3 note/checklist task can warrant C-S2, whereas a C3 calendar/reminder task can warrant C-S3; both are assigned only if both functions are explicitly required. Likewise M2 may support keyboard adaptation (M-S1), acceptance/timing adaptation (M-S3), or both. Group and subgroup annotations describe the accessibility condition to be supported at completion or user takeover, not the agent's required observation modality or interaction path. These labels are metadata for analysis, not clinical inference. Existing task records and subgroup-level statistics require task-by-task reassignment before they can be reported as finalized.

The everyday workflow categories are communication, information, management, mobility, consumption, service, health, and access. Motivated by prior evidence that CAPTCHA is a major accessibility barrier for screen-reader users \citep{webaimsr}, CAPTCHA is reported separately as a cross-cutting verification-barrier stress test rather than interpreted as a need or a daily-life workflow category. Each CAPTCHA task is assigned the underlying visual or hearing need exercised by its challenge modality.

\paragraph{Task schema.}

\paragraph{Self-hosted services.}
The current Windows implementation uses OneStopShop (7770), an e-commerce CMS/admin service (7780), Kiwix Wikipedia (8888), a Reddit-style forum (9999), and a local CAPTCHA service (8765). Exact image versions, reset procedures, and evaluator access methods will be frozen in the artifact release. \todo{Insert release commit/hash and container versions.}

\paragraph{Cross-run service isolation.}
A generated service manifest maps each shared service to the IDs of tasks that access it. OneStopShop and the CMS receive host-global exclusive lanes because task setup and execution reset or modify their shared Magento state. Wikipedia and the forum are read-only in the current task set and therefore require no lane. CAPTCHA challenges are deterministic functions of challenge type and seed, and their evaluators inspect the success URL in each task's isolated browser rather than shared server records, so CAPTCHA tasks also run concurrently.

Each experiment run maintains a dynamic queue shared by its workers. Before claiming a task, a worker attempts to acquire every required global lane without blocking. If acquisition fails, the worker leaves that task pending and scans subsequent tasks; a short per-run queue lock makes task claiming atomic without serializing execution. When no pending task is currently runnable, the worker polls until a required lane becomes available. Acquired lanes are held across environment setup, agent interaction, and terminal evaluation, and are released only after the task container exits. Thus both workers within one run and workers in independently launched runs are prevented from concurrently accessing the same mutable backend. The protocol guarantees mutual exclusion rather than cross-run fairness: a run may reacquire a released lane for its next pending task before another run obtains it.

Lane acquisition precedes VM-overlay preparation and task-container launch. Consequently, lane waiting is outside the agent-side timer, which begins only after environment reset, and does not contribute to the reported per-task execution time, token count, or step count. We record per-worker lane-wait duration separately in a scheduler log. This separation preserves agent-efficiency measurements while making additional wall-clock delay from shared-service isolation observable.

\paragraph{Hearing-media provenance.}
For fixed TTS tasks, release metadata should include the canonical script, generated audio asset, provider/model/voice/version, expected continuous caption phrases or atomic facts, duration, required caption feature, generation date, and file hash. The construction script is never exposed to the agent as task input.

\section{Task Curation and Cross-Validation Details}

Three annotators with at least undergraduate-level training in computer science manually constructed the benchmark. Each task authored by one annotator was reviewed and manually executed by the other two during three rounds of cross-validation. Review covered feasibility, instruction clarity, task--need fit, consistency with the documented need and its supporting real-user/accessibility evidence, reproducibility of the setup, and evaluator correctness. The counterfactual relevance check asked whether removing the access-specific requirement would leave the required information, artifact, persistent state, or evaluator essentially unchanged; tasks failing this check were revised, reassigned, or removed. In total, construction and validation required approximately 600 person-hours (about two hours of construction and one hour of validation/revision per task). \todo{Report counts of tasks revised/reassigned/removed across rounds and the final number of initialization functions/configurations and executable evaluation metrics.}

\section{Complete Cross-Method Failure Analysis}

\subsection{Scope and coding rule}

We analyze the current top-level results for Agent S3, CoAct, LocalLSTC, and HISA without pattern memory, each using Qwen3.8-27B on the same 198 tasks. A run fails when its executable evaluator score in \texttt{result.txt} is below one. The analysis uses all 792 result records and their available execution logs; it does not treat four configurations on the same task as independent samples. The mechanism labels below are an audit synthesis rather than a completed multi-annotator study, so no inter-annotator agreement is claimed.

We use two levels of description. The first names a generic execution cause: missing evidence, grounding or actuation error, constraint loss, cross-application transfer error, persistence/save failure, inference under uncertain perception, repeated recovery or budget exhaustion, premature termination, environment infeasibility, or scaffold/controller failure. The second records the accessibility-conditioned consequence: incomplete accessible information, a missing/stale/incorrect persistent artifact, an unestablished assistive or continuation state, a delegated interaction barrier that remains, increased user verification/recovery burden, or no handoff failure when $H=1$ but $T=0$. This separation prevents an ordinary GUI error from being redescribed as disability-specific while retaining its effect on the state returned to the user.

\subsection{Recurring causes and accessibility consequences}

\paragraph{Premature completion and incomplete verification.}
Agent S3 reports completion in 56 failed runs, CoAct terminates in 52, LocalLSTC finishes in 52, and HISA records \texttt{Task COMPLETED} in 73. Among these, 47, 47, 43, and 63 respectively have $H=0$. Although the four terminal actions are not architecturally identical, all exhibit the same failure pattern: a local visible change, object existence check, or plausible final summary substitutes for re-reading the authoritative end state and checking every conjunctive requirement. This is the strongest recurring mechanism in the logs.

\paragraph{Non-convergent recovery.}
Long failures repeatedly scroll, click adjacent controls with small coordinate changes, alternate between GUI and code paths without reconciling state, or continue exploration until no budget remains for persistence and verification. Agent S3 has 23 failed runs that reach 50 steps and 16 additional nonterminal stops. CoAct has 68 no-terminal failures with at least 50 logged actions. LocalLSTC has 22 failures at the 50-step limit and 12 stopped by its three-stall rule. HISA has 31 failures at the 50-step limit and six planner-declared infeasible runs. These measures are scaffold-specific and not directly interchangeable, but they consistently show weak bounded recovery.

\paragraph{Grounding, actuation, and exact settings.}
Errors include clicking a chevron beside a toggle, focusing the wrong field, assuming an ineffective click succeeded, or losing the target after zoom, scrolling, or window changes. Exact magnification and text size, color filters, Filter/Sticky/Mouse Keys subsettings, ClickLock, primary-button selection, audio flash/mono options, and caption presentation require more than opening the relevant settings page. The generic cause is control and state-estimation error; the handoff consequence is a configuration that cannot support user continuation.

\paragraph{Evidence transfer and persistence.}
Dates, codes, quantities, and ordered facts may be incompletely transferred from audio, PDFs, images, or web pages into email, calendar, notes, spreadsheets, or CMS fields. Save, Save As, auto-save, and Save-and-Close semantics add another failure point, and code-level edits may not refresh an application's cached view. Existence-only checks miss stale or semantically incorrect artifacts. This mechanism explains both missing handoff support and confidently wrong external memory.

\paragraph{Uncertain perception and accessible representations.}
When OCR or visual inspection is ambiguous, all four systems sometimes complete a map route, product relation, image description, or PDF answer with a plausible but unsupported inference. V3 failure rates are 55.0\%, 70.0\%, 45.0\%, and 50.0\% for Agent S3, CoAct, LocalLSTC, and HISA. The error is not unique to accessibility, but an unverified textual representation may be the user's only available account of the non-text content.

\paragraph{Delegated precision barriers.}
Hold, slide, drag, patch selection, and fine target acquisition are unstable for all four systems. An unsuccessful proxy action has a particular consequence for M4 tasks: it leaves intact the interaction barrier for which the user delegated the task. The benchmark changes the practical interpretation of a generic control failure; it does not posit a separate motor-specific algorithmic mechanism.

\subsection{Observation-channel limitation for transient captions}

The H1 failures expose a limitation of the observation interface as well as of the planner. The baseline does not receive a continuous caption transcript or an audio stream. It obtains screenshots at action and observation boundaries and must read whatever portion of the Live Caption overlay happens to be visible in those frames. Captions are transient: text may appear and disappear between two screenshots, a later utterance may overwrite an earlier one, and a single frame may contain only a suffix of the information needed for the task. Enabling Live Caption can therefore satisfy the measured access state while leaving the agent without a complete record of dates, codes, quantities, alternatives, or their order. No amount of reasoning over the observed frames can recover an utterance that was never captured.

This mechanism is visible in downstream artifacts. In \nolinkurl{communication-dental_reschedule_voicemail}, the system leaves Live Caption enabled and persists Thunderbird drafts, but its body omits required fields such as the weekday and year and normalizes the confirmation code incompletely; the run receives $H=1,T=0$. Other H1 runs similarly obtain the accessibility state but fail when converting transient speech into an email, note, calendar entry, CMS update, or factual answer. We therefore code these cases separately from failures in which the agent saw the relevant caption evidence but later lost or miscopied it. The former are observation-coverage failures induced by temporally sparse screenshot sampling; the latter are planning, memory, transfer, or artifact-construction failures.

This finding is specific to the evaluated scaffold rather than an unavoidable property of caption-based assistance. A continuous caption-event stream, transcript buffer, denser temporally triggered observations, or an explicit replay-and-accumulate policy could expose the missing evidence. This case identifies a weakness in that particular baseline's observations when handling the nominal speech-content task, not an H1 requirement that the agent must read captions. Preserving the caption feature and accurately completing the nominal task remain separate checks.

\subsection{GUI-grounding errors and accessibility consequences}

The GUI grounder does not always localize the intended control accurately. A mis-grounded click can activate a neighboring control, place focus in the wrong field, alter an unintended setting, or leave the interface unchanged while the agent assumes progress. Repeated attempts then consume the interaction budget and can propagate stale state into later actions. These are familiar GUI-agent failures, but their consequences are amplified in accessibility-oriented use. Blind and low-vision users may be unable to visually inspect the resulting screen, identify which control was activated, or independently reverse an unintended change. An apparently small grounding error can therefore increase the burden of verification, recovery, and handoff, and may leave the user in a less usable interface state than before delegation.

Trajectory coding treats incorrect target localization as a grounding failure and records its downstream consequence separately: nominal-task corruption, failure to preserve an accessibility setting, or loss of a usable continuation state. This separation avoids presenting grounding as unique to disability while capturing why the same error can be more costly when the user relies on the agent for nonvisual access or proxy interaction.

\subsection{Representative failure mechanisms}

The following patterns recur in the inspected trajectories.

\paragraph{Partial verification and false completion.}
The agent frequently verifies that an action produced some visible or file-level change without checking all task constraints. In \nolinkurl{captcha-hold_button_1}, the button changes to \emph{Complete} and the progress bar fills, after which the agent terminates; the evaluator requires navigation to the success URL, implying that an additional continuation action remains. In \nolinkurl{information-cat_image_alt_text}, the agent verifies only that a description attribute exists in the DOCX package. The saved description mentions a cat and car hood but omits task-relevant visual attributes required by the evaluator. These are general termination and constraint-coverage errors whose consequence is an incomplete accessible result.

\paragraph{Plausible inference after failed perception.}
When OCR or visual inspection remains ambiguous, the agent sometimes substitutes world knowledge or a locally plausible relation for evidence from the supplied artifact. In \nolinkurl{mobility-cta_airport_transfer}, it correctly identifies O'Hare, the Blue Line, Clark/Lake, and Midway, but writes Green Line rather than the required Orange Line. The trajectory explicitly records uncertainty in OCR before the model nonetheless describes its answer as verified. This mechanism is shared with ordinary visual benchmarks; the accessibility-specific consequence is that the generated textual route is intended to replace visual access to the map and must therefore be evidence-complete.

\paragraph{Persistent artifact updated despite an incorrect nominal result.}
In cognitive consumption tasks, the model can update a checklist or spreadsheet status while selecting the wrong item or variant in the web workflow. For example, \nolinkurl{consumption-lowest_price_white_mouse} changes the spreadsheet's Mouse status to \texttt{Done} and saves a product note, satisfying the persistent-memory component, but the cart does not contain the required product and option. The support artifact can therefore become confidently wrong, which is more consequential than simply omitting it because it may guide subsequent user action.

\paragraph{Exact assistive-state configuration.}
The model is more reliable at opening common accessibility features than at selecting exact variants or parameter values. It succeeds on opening Magnifier, Narrator, the on-screen keyboard, Mouse Keys, and Sticky Keys in several tasks, but fails on examples requiring 200\% magnification, a particular color-vision filter, ClickLock, Filter Keys, a specified audio-flash mode, or a swapped primary mouse button. These failures combine generic settings navigation with a benchmark-specific continuation-state requirement: the requested configuration must remain correct when control returns to the user.

\paragraph{Sustained and precision pointer interaction.}
Simple clicks and checkboxes are substantially easier than hold, slide, patch-selection, and other continuous or precision-dependent challenges. This is a generic control limitation, but the M4 tasks expose it specifically where the user delegated the interaction because sustained or precise pointer control is inaccessible. The benchmark therefore changes the practical interpretation of the same low-level failure: an unsuccessful proxy action leaves the original access barrier in place.

\subsection{Complex-PDF case: layout-aware visual verification}
\label{app:polisher_pdf_case}

Task \nolinkurl{consumption-cheapest_polisher} provides a representative case in which a document's text layer is useful for retrieval but unreliable for final semantic verification. The source is a 57-page, untagged Harbor Freight catalogue with dense multi-column product blocks, interleaved names, item numbers, sale prices, comparison prices, and promotional text. Its embedded text is therefore not read in the same two-dimensional order in which the page is visually organized. The complete released instruction is:

\begin{quote}
\small
\textbf{Instruction.} I have difficulty using a physical keyboard. Open the Windows On-Screen Keyboard and leave it available for me. Find the cheapest polisher in the provided Harbor Freight catalogue and save its full product name exactly as shown on the first line and its price on the second line of \texttt{answer.txt} on the Desktop.
\end{quote}

A text-only strategy repeatedly formed plausible but incorrect name--price associations. On physical PDF page~6, extraction placed \texttt{\$19.99} before the line \texttt{6" PALM POLISHER} and \texttt{\$109.99} after its item number, making nearest-line matching assign the wrong price. Page~13 contained the lexically cheaper \texttt{6 PIECE POLISHER ACCESSORY KIT} at \texttt{\$14.99}, although it is an accessory rather than a polisher. On page~17, a nearby \texttt{\$9.99} belonged to a cut-off tool, while the actual \texttt{3" POLISHER KIT} cost \texttt{\$34.99}. These errors are not resolved by extracting more neighboring lines because the missing relation is spatial: product names and prices occupy aligned visual blocks rather than a reliable linear text sequence.

The successful trajectory used the two PDF APIs as complementary channels. First, \texttt{PdfTools.extract\_text} stored the complete text with explicit physical-page markers. A keyword search reduced 57 pages to candidate pages 6, 13, and 17. Second, \texttt{PdfTools.render\_page} rendered each candidate page and returned the PNG directly as the first visual input to the planner, avoiding viewer chrome, viewport cropping, and desktop-resolution downsampling. The agent first identified the \texttt{\$19.99} palm polisher on page~6. It then inspected page~17 to reject the text-derived \texttt{\$9.99} hypothesis, inspected page~13 to classify the \texttt{\$14.99} result as an accessory kit, and finally re-rendered page~6 at 200~DPI to verify the exact output string. It wrote \texttt{6" PALM POLISHER} and \texttt{\$19.99} to \texttt{answer.txt}, left the On-Screen Keyboard open, and received full executable credit. Table~\ref{tab:polisher-disambiguation} summarizes the disambiguation, and Figure~\ref{fig:polisher-pdf-evidence} shows the rendered evidence supplied to the model.

\subsection{Implications for model and scaffold design}

The case study motivates four handoff-stage interventions. First, an explicit ledger for nominal $G$ and handoff $H_u$ obligations prevents apparently complete tasks from hiding an unverified artifact or accessibility state. Second, transient evidence such as captions should be buffered before conversion into durable user-facing information. Third, grounding uncertainty should trigger independent state inspection before the agent claims that the requested interface is ready. Fourth, bounded recovery should target the failed delivery condition rather than repeat unproductive interactions. LocalLSTC2 operationalizes the first intervention through fixed completion conditions and condition-level verification, and preserves cross-stage evidence through global facts. Audio transcription further supplies durable speech evidence, while PDF text extraction and page rendering support complementary textual and spatial inspection. These mechanisms target properties of the state returned to the user without requiring the agent to adopt the user's assistive tool as its own perceptual channel.

External experiments on OSWorld and WindowsAgentArena can test general GUI transfer and overhead, but those benchmarks cannot directly establish handoff readiness without need-conditioned handoff evaluators.

\section{Additional Task-Construction Examples}
\label{app:construction_examples}

The eight examples below complement the H1 management example in Figure~\ref{fig:pipeline}. They retain the recorded user instructions and benchmark evaluators. Several instructions explicitly say ``use'' a named assistive tool even though the evaluator checks only the final support state. These instances must be revised or explicitly identified as process-specific exceptions before claiming that the release is entirely source agnostic. Unless process use is directly evaluated, named assistive tools are treated as user-facing handoff requirements rather than prescribed agent strategies. We select two tasks per functional group and one task from each non-CAPTCHA workflow category. Every selected task received an A naturalness rating and a low runtime web-risk rating in our task audit. Each example reproduces the complete user-facing instruction from the released task JSON, then identifies how its setup and evaluator make the accessibility-oriented completion condition executable.

\subsection{Visual}

\paragraph{Mobility: finding the nearest pharmacy.}
Task \nolinkurl{mobility-nearest_pharmacy_marina_bay_sands} represents V1 non-visual access in a mobility workflow. \textbf{Instruction.} I rely on a screen reader to follow the content. Turn on Windows Narrator and use the provided walking-distance directory with Marina Bay Sands, Singapore as the current location. Choose the pharmacy with the shortest displayed walking distance, breaking a tie by the shorter walking time, then open that pharmacy's place details and leave them open. \textbf{Construction and evaluation.} Setup opens a fixed local HTML directory in Chrome with eight fully interactive, non-ranked candidates, avoiding dependence on a live map or directory. Two candidates share the shortest distance, so the walking-time tie-break is necessary. Full success requires both Narrator to remain enabled and the selected detail view to contain the correct pharmacy name, address, 0.4-km distance, and six-minute walking time.

\paragraph{Consumption: purchasing a catalogued product.}
Task \nolinkurl{consumption-lavender_coupon} exercises V1 in an online-shopping workflow. \textbf{Instruction.} I rely on a screen reader to shop online. Turn on Windows Narrator, then use OneStopShop to find the French Provence live lavender plant with blue flowers that comes as one plant in a 2.5-quart pot. Add exactly one unit to the shopping cart, enter coupon code \texttt{LAVENDER20} without applying it, and leave the cart page open. \textbf{Construction and evaluation.} Setup resets and opens the self-hosted storefront. Conjunctive checks require Narrator, the exact product and quantity, coupon code \texttt{LAVENDER20}, and the cart as the active page.

\subsection{Hearing}

\paragraph{Communication: responding to a dental voicemail.}
Task \nolinkurl{communication-dental_reschedule_voicemail} instantiates H1 text/non-auditory access to speech and H4 audio-channel adaptation in an email workflow. \textbf{Instruction.} I hear primarily through one ear and rely on captions for clarity. Turn on Mono audio, then use Chrome Live Caption to read the dental voicemail on the Desktop. Choose the earlier of the two offered appointments and create and save a Thunderbird draft to \texttt{appointments@example.com} with subject \texttt{Dental reschedule}, including the chosen date, time, and confirmation code. Do not send it. \textbf{Construction and evaluation.} Setup opens a fixed MP3 in Chrome and prepares Thunderbird. Accessibility evaluators require both Mono audio and Live Caption to remain enabled; the outcome evaluator checks the recipient, subject, and the four required body facts for the September 17 appointment.

\paragraph{Service: recording council pickup instructions.}
Task \nolinkurl{service-council_document_pickup_audio} applies H1 text/non-auditory access and H2 caption presentation to a public-service workflow. \textbf{Instruction.} I cannot reliably hear the recording and need larger captions. Use Windows Live captions with the caption style set to Large text to read the council service recording on the Desktop. Save the pickup location, collection hours, item to bring, and reference number to \texttt{answer.txt}, one item per line in that order. \textbf{Construction and evaluation.} A pinned local recording removes public-media drift. Accessibility evaluators require Windows Live captions to remain enabled with the Large text style; the outcome evaluator applies ordered, line-based content checks for Civic Service Centre counter 4, the collection hours, photo identification, and reference \texttt{PS-482}.

\subsection{Motor}

\paragraph{Access: enabling alternative pointer control.}
Task \nolinkurl{access-enable_mouse_keys} directly realizes M3 alternative/adapted pointer control. \textbf{Instruction.} Precise mouse control is difficult for me. Turn on Windows Mouse Keys and leave it enabled for me. \textbf{Construction and evaluation.} No external content or network setup is required. The evaluator reads the current user's Windows Mouse Keys flags and accepts only the enabled state, making the requested continuation state the graded result.

\paragraph{Health: preserving an alternative text-entry interface.}
Task \nolinkurl{health-insulin_storage_temperature} instantiates M1 in a health-information workflow. \textbf{Instruction.} I have difficulty using a physical keyboard. Open the Windows On-Screen Keyboard and leave it available for me. Save only the recommended refrigerated temperature range for unopened insulin from the provided insulin-storage PDF in \texttt{answer.txt} on the Desktop. \textbf{Construction and evaluation.} Setup opens a fixed local PDF in Chrome. Full success requires a visible On-Screen Keyboard process and an \texttt{answer.txt} file containing the accepted 36--46\,$^{\circ}$F range.

\subsection{Cognitive}

\paragraph{Management: creating a prospective-memory cue.}
Task \nolinkurl{management-prescription_refill_reminder} represents the prospective-memory realization of C3 (ISO 6-3-4). \textbf{Instruction.} I rely on reminders and time cues to keep track of future actions. Create an all-day Thunderbird Calendar reminder titled \texttt{Refill medication} for the refill deadline in the pharmacy message on the Desktop. \textbf{Construction and evaluation.} Setup creates a fixed desktop message and prepares a Thunderbird profile. A structured calendar evaluator checks the title, July 20, 2026 date, all-day duration, and time fields. The nominal and accessibility outcomes coincide because the reminder itself is the requested support artifact.

\paragraph{Information: externalizing reference locations.}
Task \nolinkurl{information-chrome_reference_bookmarks} realizes the persistent-record realization of C3 (ISO 6-3-4) in an information workflow. \textbf{Instruction.} I rely on persistent written records so I do not have to remember important details. Save the two already-open local Wikipedia reference pages \texttt{Accessibility} and \texttt{Computer accessibility} as persistent bookmarks on the Chrome bookmark bar so they can be reopened without having to remember or search for them again. \textbf{Construction and evaluation.} Setup opens two fixed Kiwix pages hosted inside the benchmark environment. The evaluator inspects Chrome's structured bookmark state and requires both exact local URLs on the bookmark bar.
