\begin{abstract}
Accessibility needs often do not change the underlying digital goal; they change what information, support, or interface state is required for usable completion. Computer-use agents (CUAs) could reduce access barriers by completing GUI workflows on users' behalf, yet current benchmarks mainly measure nominal task completion and provide little evidence about whether agents can satisfy accessibility-related requirements. \section{Introduction}

More than 1.3 billion people---approximately one in six people worldwide---experience significant disability \citep{whodisability}. GUI agents have substantial potential to improve computer access for people with disabilities by perceiving interfaces and executing multi-step interactions on their behalf. Yet accessibility remains only lightly studied in computer-use agents, and existing general-purpose benchmarks largely evaluate a homogeneous notion of task completion.

Recent work suggests that the accessibility problem is not well captured by inventing a separate class of ``disabled-user tasks.'' A11y-CUA places sighted and blind/low-vision users on the same 60 everyday Windows tasks, showing that high-level goals can be shared even when accessible perception, control, and monitoring differ substantially \citep{a11ycua}. Complementarily, Kodandaram et al. study blind screen-reader users using a desktop CUA in naturalistic workflows; the resulting commands center on familiar desktop activities such as document editing, spreadsheet operations, application configuration, and file management \citep{arewethereyet}. Their interviews further show that blind users do not envision CUAs only as end-to-end automation: they also want collaborative support for understanding unfamiliar interfaces, obtaining situated help, troubleshooting breakdowns, learning workflows, and retaining control over consequential actions \citep{arewethereyet}. Taken together, these findings motivate a distinction between the \emph{underlying activity} and the \emph{conditions for usable assistance}. Accessibility-oriented evaluation should therefore preserve ordinary user goals while testing whether an agent produces the information, support, and user-facing state needed for those goals to be usable.

To address this gap, we introduce \bench, an executable Windows benchmark with 200 tasks spanning visual, hearing, motor, and cognitive functional groups. We first synthesize recurring accessibility needs from accessibility research, user surveys and stories, standards and design guidance, and platform documentation; we then use the resulting need taxonomy as the systematic unit for constructing controlled, executable tasks. Rather than constructing disability-exclusive activities or requiring agents to imitate a prescribed assistive-technology trajectory, we instantiate documented needs within ordinary workflows and make the resulting access requirement part of the graded end state. This operationalizes one prerequisite for assistive collaboration: when a user delegates execution, the agent should leave a usable, access-supporting result rather than merely reach a nominal task endpoint.

Accessibility-oriented evaluation also requires distinguishing nominal task completion from completion of the accessibility-specific requirement. An agent may, for example, place the correct items in a shopping cart while failing to update a checklist used for memory support, or complete a workflow while leaving a required accessibility setting disabled. We therefore decompose task success, where applicable, into the ordinary \taskout and the accessibility-specific \accessreq, enabling direct measurement of cases in which an agent completes the nominal workflow but still fails to satisfy the user's need.

We evaluate five recent computer-use agents---Agent S3 \citep{agents3}, CoAct-1 \citep{coact1}, GTA1 \citep{gta1}, HiSA \citep{hisa}, and LocalLSTC \citep{locallstc}---on OSWorld, WindowsAgentArena, and \bench under matched 15- and 50-step budgets. \todo{Insert headline cross-benchmark result.} \todo{Insert result on the effect of longer interaction budgets.} Decomposed evaluation further shows \todo{insert TaskOutcome--AccessRequirement gap}, while controlling for task difficulty and operating time indicates that \todo{insert complexity-controlled result}. \section{Related Work}

\paragraph{General computer-use benchmarks.}
WebArena and VisualWebArena evaluate realistic web interaction \citep{webarena,visualwebarena}; OSWorld extends executable evaluation to desktop applications and operating-system settings \citep{osworld}; WindowsAgentArena and AndroidWorld provide scalable desktop and mobile environments \citep{waa,androidworld}. Spider2-V applies execution-based evaluation to professional data workflows \citep{spider2v}, while VideoGUI, VideoWebArena, and OmniGUI broaden multimodal GUI evaluation \citep{videogui,videowebarena,omnigui}. These benchmarks establish reproducible environments, automatic initialization, and end-state evaluation for general computer use. Their primary construct, however, is whether an agent completes the nominal GUI goal; heterogeneous access needs are not explicitly represented as task-level completion conditions. \bench retains the executable-benchmark methodology but changes the construct being measured: a documented access need may alter the information that must be acquired, the user-facing representation or support artifact that must be produced, or the accessibility/continuation state that must be established or preserved.

\paragraph{Accessibility-oriented CUA studies.}
A11y-CUA is the closest prior work on accessibility-conditioned computer use \citep{a11ycua}. It contributes a dataset of sighted and blind/low-vision users performing the same 60 everyday Windows tasks and compares human traces with CUAs under default and accessibility-related interaction conditions. This matched-task design is important for our framing: accessibility does not necessarily imply a different high-level task distribution; the same goals can impose different requirements on perception, control, feedback, and collaboration. A11y-CUA shows substantial performance degradation under keyboard-only and magnified conditions and reveals systematic differences between sighted, blind/low-vision, and agent interaction strategies. Its central object, however, is accessibility-conditioned interaction and trajectory behavior, with a primary emphasis on blind/low-vision users; it does not aim to construct a cross-need executable benchmark in which heterogeneous accessibility requirements systematically modify the graded end state.

Kodandaram et al. provide complementary ecological evidence through a three-week diary study of eight blind screen-reader users interacting with a desktop CUA across 12 applications \citep{arewethereyet}. Their 1,258 participant-issued commands span ordinary desktop activities such as document editing, spreadsheet operations, application configuration, presentation editing, and file management, while their replay evaluation identifies grounding, planning, constraint-tracking, and termination failures. Crucially, interviews show that participants wanted CUAs not only to execute tasks autonomously, but also to explain unfamiliar interfaces, provide situated troubleshooting and recovery support, help users learn workflows, and preserve user control around consequential actions. This positions an accessible CUA as a collaborative assistive system rather than merely an automation engine. In contrast, our goal is not to characterize one population's naturalistic use of a screen-reader-accessible agent, but to operationalize one component of usable assistance in a controlled, reproducible evaluation across documented visual, hearing, motor, and cognitive needs: whether delegated completion satisfies both the nominal task and the access-need-specific requirement.

\paragraph{User assistance and intent-aware systems.}
GUIDE studies user intent, task progress, and assistance opportunities in open-ended GUI workflows \citep{guide}. Such work is complementary to ours: it asks when and how a system should assist a user, whereas \bench evaluates whether an autonomous CUA can complete an accessibility-oriented user goal once assistance is delegated. More broadly, these lines of work motivate user-aware agents, while our contribution is an executable benchmark construct and evaluation methodology for measuring access-need-specific end-state success.

\subsection{Task Definition}

Following prior executable computer-use benchmarks \citep{osworld,waa}, we formalize agent interaction with the desktop environment as a partially observable Markov decision process (POMDP)
\begin{equation}
\mathcal{M}=(\mathcal{S},\mathcal{O},\mathcal{A},\mathcal{P}),
\end{equation}
where $\mathcal{S}$ is the desktop state space, $\mathcal{O}$ the observation space exposed by an agent's scaffold, $\mathcal{A}$ the permitted action space, and $\mathcal{P}(s_{t+1}\mid s_t,a_t)$ the environment transition dynamics. Given an observation $o_t\in\mathcal{O}$ of the current state $s_t$, the agent selects an action $a_t\in\mathcal{A}$ and transitions the environment to $s_{t+1}$. The interaction terminates when the agent declares completion or reaches the maximum step budget.

An accessibility-oriented task is defined as
\begin{equation}
\tau=(I,s_0,G,R),
\end{equation}
where $I$ is a natural-language instruction, $s_0$ the initialized desktop state, $G$ the nominal task goal, and $R$ an accessibility requirement induced by the user's accessibility need. Starting from $s_0$, the agent produces a terminal state $s_T$. We distinguish two conditions on this state: $E_{\mathrm{task}}^\tau(s_T)$ indicates whether $G$ is satisfied, and $E_{\mathrm{access}}^\tau(s_T)$ indicates whether $R$ is satisfied. For binary tasks,
\begin{equation}
E_{\mathrm{full}}^\tau(s_T)
=E_{\mathrm{task}}^\tau(s_T)\land E_{\mathrm{access}}^\tau(s_T).
\end{equation}
This formulation captures cases in which an agent completes the nominal GUI workflow while leaving the accessibility requirement unmet. We evaluate the resulting user-facing state rather than requiring agents to imitate the interaction strategy of a person with a disability. This distinction is deliberate: prior human data show that sighted and blind/low-vision users can pursue the same task goals through heterogeneous interaction strategies \citep{a11ycua}, while blind users may value CUA support that helps them understand, recover, or learn without fully delegating the task \citep{arewethereyet}. Although \bench evaluates delegated completion rather than mixed-initiative interaction itself, it specifies what must be true for usable completion, not how the agent must get there.

\subsection{Task Construction}

The central design principle of \bench is \emph{evidence-informed, need-driven task construction}. We first derive and ground the need taxonomy in external accessibility evidence; task synthesis then begins from a documented need, determines how that need changes a usable completion condition, and instantiates the requirement in a controlled everyday GUI workflow consistent with the observed user behaviors associated with that need. This separates evidence gathering from benchmark synthesis and prevents accessibility relevance from being assigned post hoc based on the presence of an assistive technology or a disability label. The construction pipeline is illustrated in Figure~\ref{fig:pipeline}.

\paragraph{A concrete construction example.}
Figure~\ref{fig:pipeline} traces one released task from need to evaluator. The starting construct is H1, which captures the need to obtain spoken information through text. We instantiate it as appointment management: a fixed recording states that a home-support assessment is scheduled for September 29, 2026 at 1:15 PM, and the user asks the agent to recover these facts with Chrome Live Caption and create a 45-minute Thunderbird event. Creating the exact event satisfies $E_{\mathrm{task}}$, but it does not satisfy $E_{\mathrm{access}}$ unless Live Caption remains enabled. The environment uploads the pinned MP3, prepares a fixed Thunderbird profile, and opens both applications. At termination, one evaluator inspects the caption setting and a second checks the structured event fields; \fullsuccess is their conjunction. Removing the H1 requirement would remove the caption state and its check without changing the calendar goal, so the example passes the counterfactual relevance test. \paragraph{Formative evidence review.}
Before task synthesis, we conducted a formative review of accessibility research, user surveys and stories, standards and design guidance, and platform documentation to identify recurring functional barriers and support needs \citep{w3cpeople,w3cstories,webaimsr,w3cauditory,w3cphysical}. We abstract these findings into the 21-need taxonomy used as the systematic unit of task construction; for each need, Appendix~\ref{app:taxonomy} also records representative observed user behaviors/scenarios and their supporting evidence. Many high-level digital goals---such as communication, information seeking, scheduling, shopping, and service access---are shared across users. This is consistent with matched-task evidence from A11y-CUA and with the ordinary desktop activities that emerge from blind users' naturalistic CUA use \citep{a11ycua,arewethereyet}. Accessibility needs can instead change the information representation, interaction conditions, persistent support, or continuation state required for usable completion.

\paragraph{Functional coverage.}
We organize tasks into four top-level functional groups---visual, hearing, motor, and cognitive---as operational slices of barriers exercised by GUI interaction, rather than as an exhaustive diagnostic taxonomy. They correspond to limitations in acquiring visual information, acquiring auditory information, executing physical input actions, and processing or maintaining task-relevant information, respectively, and are consistent with common accessibility framings of sight, hearing, movement, and cognitive abilities \citep{w3cpeople}. A functional organization is preferable to diagnosis-based grouping for our purpose because the same diagnosis can produce heterogeneous interaction needs, while similar GUI barriers can arise across diagnoses. We additionally annotate broad functional subgroups for finer-grained analysis, but treat them only as secondary, potentially overlapping labels; their definitions and mappings are given in Appendix~\ref{app:taxonomy}.

\paragraph{Why construct from needs?}
After the formative review, the 21 need IDs serve as the lowest-level constructs used to generate tasks. Each describes a functional barrier or support requirement rather than a particular application or assistive technology. Using needs as the construction unit provides systematic coverage, separates a user requirement from any single implementation, and gives a reproducible unit for task design and validation. Every released core task maps to at least one documented need, and that need must materially change at least one observable completion condition: the information to be acquired, the user-facing representation or support artifact to be produced, or the accessibility/continuation state to be established or preserved. The resulting taxonomy contains 6 visual, 5 hearing, 7 motor, and 3 cognitive need IDs; the full definitions and evidence sources are provided in Appendix~\ref{app:taxonomy}. We intentionally keep the cognitive taxonomy narrow: generic planning burden, long horizons, arithmetic, or decision difficulty alone do not qualify unless they induce an observable accessibility-support requirement.

\paragraph{Why these workflows?}
Need IDs describe \emph{why} a task is accessibility-oriented; workflow categories describe \emph{what everyday activity} is being performed. To obtain broad life-domain coverage without inventing disability-exclusive activities, we use the WHO ICF Activities and Participation component as a coverage guide rather than reproducing its hierarchy verbatim \citep{whoicf}. This choice also reflects empirical evidence that sighted and blind/low-vision users often pursue the same everyday computer goals \citep{a11ycua}, and that blind users naturally delegate familiar desktop work to CUAs \citep{arewethereyet}. We therefore consolidate relevant digital activities into eight benchmark-specific everyday workflow categories: \textit{communication}, \textit{information}, \textit{management}, \textit{mobility}, \textit{consumption}, \textit{service}, \textit{health}, and \textit{access}. These categories are orthogonal to user groups and need IDs: the same workflow can exercise different access needs, and the same need can appear in multiple workflows. Accessibility enters the benchmark through the required information, support artifact, or persistent state, rather than through a separate set of supposedly disability-specific activities. CAPTCHA is a particularly salient accessibility barrier for screen-reader users; in WebAIM's 2024 Screen Reader User Survey, it was rated the most problematic web accessibility item \citep{webaimsr}. We therefore include \textit{captcha} as a ninth category, reported separately as a deterministic verification-barrier stress test rather than interpreted as an everyday-life domain. Crossing documented needs with everyday workflows reduces a one-to-one coupling between disability group, application, and task type, and allows later analysis to separate need-related effects from workflow-specific difficulty.

\paragraph{Construction procedure.}
For each task, annotators first select a documented need, then instantiate it in an everyday scenario consistent with the observed user behavior/context documented for that need and determine how the need changes the required outcome. They write a concise user instruction, instantiate the scenario in the Windows environment, and implement both the initial-state configuration and the executable end-state evaluator. Every requirement stated in the instruction is mapped to an observable final-state check. For example, a C2 memory-support task may require both a correct shopping-cart state and an updated persistent checklist; a hearing task may require recovered spoken facts in a non-auditory representation; and a motor task may require a requested keyboard-assistance state to remain enabled after the underlying workflow is completed.

We apply a task-level counterfactual relevance check during construction: \emph{if the accessibility-specific requirement were removed, would the required information, user-facing artifact, persistent state, or evaluator remain essentially unchanged?} If so, the task does not exhibit a sufficiently strong accessibility construct and is revised, reassigned, or removed. This criterion rules out ordinary GUI tasks augmented with arbitrary accessibility labels or unrelated toggles, while allowing ordinary life goals whose usable completion conditions genuinely change under a documented access need.

\paragraph{Manual annotation and cross-validation.}
All tasks were manually constructed by three annotators, each with at least undergraduate-level training in computer science. We conducted three rounds of cross-validation. Every task authored by one annotator was manually evaluated and checked by the other two annotators, who verified task feasibility, instruction clarity, task--need alignment, consistency with the documented need and its supporting evidence, reproducibility of the initial state, and correctness of the evaluator. Reviewers also executed the task manually and checked that valid solutions were accepted and plausible incorrect states were rejected. Identified issues were revised and re-checked before inclusion in the benchmark. Thus, every released task was authored by one annotator and independently examined by the other two.

Task construction and validation required approximately 600 person-hours in total, or about three person-hours per task: roughly two hours for task design and implementation and one hour for cross-validation and revision. \subsection{Environment and Execution}

To ensure that every run starts from the same $s_0$, we reset a preconfigured Windows environment and execute task-specific setup functions before the agent begins. Depending on the task, setup can place source files or media on the desktop, open an application or webpage, restore a cart or local database, prepare an email or calendar state, or set an accessibility feature to a known value. We build on the OSWorld/WindowsAgentArena execution stack \citep{osworld,waa} and use common Windows applications such as Edge/Chrome, Thunderbird Mail and Calendar, Sticky Notes, Notepad, LibreOffice, Windows Settings, and built-in accessibility features.

Some web tasks use self-hosted or pinned services when a live website would make the initial state or expected answer unstable. These include shopping, CMS, Wikipedia, forum, and CAPTCHA workflows. Hearing tasks use short pinned media or fixed task-specific audio when reproducibility requires it. The benchmark therefore preserves normal GUI interaction while keeping the state seen by different agents comparable across runs. Deployment details are provided in Appendix~\ref{app:implementation}.

\subsection{Evaluation}

After an agent stops, task-specific evaluators retrieve the state relevant to the instruction and compare it with the expected result. The evaluators take three broad forms: \textbf{structured-state checks} for settings, browser state, carts, calendar entries, mail fields, and spreadsheet cells; \textbf{artifact checks} for files, notes, or other saved outputs; and \textbf{content checks} for information recovered from text, images, or audio. Natural-language content is decomposed into required facts rather than matched as a single exact string, while fields such as dates, recipients, URLs, quantities, and settings are checked structurally whenever possible.

For reporting, we denote $E_{\mathrm{task}}$, $E_{\mathrm{access}}$, and $E_{\mathrm{full}}$ as \taskout, \accessreq, and \fullsuccess, respectively. On the subset $D$ where the nominal outcome and accessibility requirement are distinct, we additionally report
\begin{equation}
\mathrm{Gap}_D=P(E_{\mathrm{task}}=1,E_{\mathrm{access}}=0\mid D),
\end{equation}
\begin{equation}
\mathrm{CRS}_D=P(E_{\mathrm{access}}=1\mid E_{\mathrm{task}}=1,D).
\end{equation}
The first quantity measures how often an agent completes the underlying workflow but misses the accessibility requirement; the second measures how often the requirement is satisfied once the underlying task is complete. Coincident tasks, such as directly creating a requested reminder or enabling a requested accessibility setting, remain in the overall \taskout/\accessreq/\fullsuccess results but are excluded from the gap calculation. \section{Conclusion}

We introduced \bench, a 200-task executable Windows benchmark for evaluating CUAs on everyday tasks shaped by diverse accessibility needs. The benchmark is built around a distinction supported by recent human-centered CUA studies: accessibility need not imply different high-level computer goals, while the conditions for usable assistance can differ; moreover, blind users may want CUAs to support understanding, recovery, learning, and user control rather than merely automate to a nominal endpoint \citep{a11ycua,arewethereyet}. \section{Limitations}

\bench is not a complete model of disability or of how any individual person uses a computer. The four functional groups are analytical slices, and real users often have overlapping, changing, and highly individual needs. Although task construction is informed by published real-user and accessibility evidence, the benchmark tasks are controlled synthetic realizations rather than direct reproductions of participant-generated tasks; this evidence-informed construction does not replace participatory or large-scale validation with target users. The benchmark also evaluates delegated task completion and user-facing end states, not the full space of mixed-initiative assistance that users may want, such as interactive explanation, clarification, teaching, or shared control \citep{arewethereyet}. The current benchmark is limited to Windows desktop interaction, and its application mix cannot represent every digital setting. Self-hosted services and fixed media improve reproducibility but remove some open-world variation. Difficulty and operating time depend on the final annotation protocol, and cross-benchmark comparisons are valid only when agent configurations and budgets are genuinely matched. Finally, deterministic evaluators may miss valid outcomes that were not anticipated during benchmark construction, and continuation-state checks measure whether future use remains possible rather than whether a user actually continues the workflow.

\section{Ethical Considerations}

The benchmark is intended to evaluate assistance, not to prescribe how people with disabilities should interact with technology or which accessibility features they should prefer. A platform feature's documented purpose does not imply that every user wants it enabled. Results for a functional group should not be interpreted as a prediction of capability for all people in that group. We also do not assume that successful assistance means maximal automation: users may prefer explanation, guidance, shared control, or confirmation while remaining engaged in the task \citep{arewethereyet}. In high-risk health, financial, identity, or other consequential workflows, user control and appropriate confirmation remain important even if an agent can technically complete the GUI task. \bench therefore should not be read as evidence that autonomous agents can replace user autonomy, accessibility expertise, or direct participation by people with disabilities in system design.

Each task has exactly one top-level \texttt{user\_group} (visual, hearing, motor, or cognitive) and one or more \texttt{need\_ids}. During curation, \texttt{subgroup\_ids} are assigned deterministically from those need IDs according to Table~\ref{tab:functional_subgroups}; this is a metadata-construction rule, not a requirement that an agent infer a user's diagnosis or subgroup at run time. The top-level group is duplicated in each task record even when it is also encoded by the task directory, keeping released examples self-contained.

The everyday workflow categories are communication, information, management, mobility, consumption, service, health, and access. Motivated by prior evidence that CAPTCHA is a major accessibility barrier for screen-reader users \citep{webaimsr}, CAPTCHA is reported separately as a verification-barrier stress test rather than interpreted as a daily-life workflow category.

\section{Evaluator DSL and Validity Study}

A compact evaluator notation expresses required text, alternatives, conjunctions, and constrained patterns:
\begin{verbatim}
"text"              = required expression
["a", "b"]          = any_of
{"all_of":[A,B]}   = require both
{"regex":"..."}   = constrained pattern
\end{verbatim}
For multi-fact outputs, score coverage over required atomic points and combine these checks with structured conditions such as recipient, date, file path, cart state, or accessibility setting. \section{Task Curation and Cross-Validation Details}

Three annotators with at least undergraduate-level training in computer science manually constructed the benchmark. Each task authored by one annotator was reviewed and manually executed by the other two during three rounds of cross-validation. Review covered feasibility, instruction clarity, task--need fit, consistency with the documented need and its supporting real-user/accessibility evidence, reproducibility of the setup, and evaluator correctness. The counterfactual relevance check asked whether removing the access-specific requirement would leave the required information, artifact, persistent state, or evaluator essentially unchanged; tasks failing this check were revised, reassigned, or removed. In total, construction and validation required approximately 600 person-hours (about two hours of construction and one hour of validation/revision per task). \todo{Report counts of tasks revised/reassigned/removed across rounds and the final number of initialization functions/configurations and executable evaluation metrics.}

This cross-validation establishes internal construct and execution quality, but it does not substitute for participatory or large-scale validation with target users with disabilities. We therefore limit our claims to evidence-informed access-need relevance rather than exhaustive representation of all users, workflows, or preferences.

\section{Additional Task-Construction Examples}
\label{app:construction_examples}

The eight examples below complement the H1 management example in Figure~\ref{fig:pipeline}. We select two tasks per functional group and one task from each non-CAPTCHA workflow category. Every selected task received an A naturalness rating and a low runtime web-risk rating in our task audit. Each example states the user-facing instruction, then identifies how its setup and evaluator make the accessibility-oriented completion condition executable.

\subsection{Visual}

\paragraph{Mobility: finding the nearest pharmacy.}
Task \nolinkurl{mobility-nearest_pharmacy_marina_bay_sands} represents V1 non-visual access in a mobility workflow. \textbf{Instruction.} The user asks the agent to turn on Windows Narrator, use a provided walking-distance directory from Marina Bay Sands, select the pharmacy with the shortest distance (breaking a tie by walking time), and leave its place details open. \textbf{Construction and evaluation.} Setup opens a fixed local HTML directory in Chrome, avoiding dependence on a live map or directory. Full success requires both Narrator to remain enabled and the selected detail view to contain the correct pharmacy name, address, 0.3-km distance, and four-minute walking time.

\paragraph{Consumption: purchasing a catalogued product.}
Task \nolinkurl{consumption-lavender_coupon} exercises V1 in an online-shopping workflow. \textbf{Instruction.} The user asks the agent to keep Narrator enabled, identify a featured lavender product and coupon from a provided garden catalogue, add exactly one matching plant to the cart, enter the coupon without applying it, and leave the cart open. \textbf{Construction and evaluation.} Setup supplies a local catalogue and resets the self-hosted storefront. Conjunctive checks require Narrator, the exact product and quantity, coupon code \texttt{LAVENDER20}, and the cart as the active page.

\subsection{Hearing}

\paragraph{Communication: responding to a dental voicemail.}
Task \nolinkurl{communication-dental_reschedule_voicemail} instantiates H1 speech-to-text access in an email workflow. \textbf{Instruction.} The user asks the agent to read a dental voicemail with Chrome Live Caption, choose the earlier of two offered appointments, and save an unsent Thunderbird draft containing the chosen date, time, and confirmation code. \textbf{Construction and evaluation.} Setup opens a fixed MP3 in Chrome and prepares Thunderbird. One evaluator requires Live Caption to remain enabled; the other checks the recipient, subject, and the four required body facts for the September 17 appointment.

\paragraph{Service: recording council pickup instructions.}
Task \nolinkurl{service-council_document_pickup_audio} applies H1 to a public-service workflow. \textbf{Instruction.} The user asks the agent to turn on Chrome Live Caption, recover pickup instructions from a council recording, and save the location, hours, required item, and reference number to \texttt{answer.txt} in that order. \textbf{Construction and evaluation.} A pinned local recording removes public-media drift. The evaluator conjoins the caption setting with ordered, line-based content checks for Civic Service Centre counter 4, the collection hours, photo identification, and reference \texttt{PS-482}.

\subsection{Motor}

\paragraph{Access: enabling alternative pointer control.}
Task \nolinkurl{access-enable_mouse_keys} directly realizes M4 alternative pointer control. \textbf{Instruction.} A user who finds precise mouse control difficult asks the agent to turn on Windows Mouse Keys and leave it enabled. \textbf{Construction and evaluation.} No external content or network setup is required. The evaluator reads the current user's Windows Mouse Keys flags and accepts only the enabled state, making the requested continuation state the graded result.

\paragraph{Health: preserving an alternative text-entry interface.}
Task \nolinkurl{health-insulin_storage_temperature} instantiates M1 in a health-information workflow. \textbf{Instruction.} A user who has difficulty with a physical keyboard asks the agent to leave the Windows On-Screen Keyboard available and save the recommended refrigerated temperature range for unopened insulin from a provided PDF. \textbf{Construction and evaluation.} Setup opens a fixed local PDF in Chrome. Full success requires a visible On-Screen Keyboard process and an \texttt{answer.txt} file containing the accepted 36--46\,$^{\circ}$F range.

\subsection{Cognitive}

\paragraph{Management: creating a prospective-memory cue.}
Task \nolinkurl{management-prescription_refill_reminder} represents C3 time and prospective-memory support. \textbf{Instruction.} The user asks the agent to read a refill deadline from a pharmacy message and create an all-day Thunderbird reminder titled \texttt{Refill medication}. \textbf{Construction and evaluation.} Setup creates a fixed desktop message and prepares a Thunderbird profile. A structured calendar evaluator checks the title, July 20, 2026 date, all-day duration, and time fields. The nominal and accessibility outcomes coincide because the reminder itself is the requested support artifact.

\paragraph{Information: externalizing reference locations.}
Task \nolinkurl{information-chrome_reference_bookmarks} realizes C2 memory externalization in an information workflow. \textbf{Instruction.} The user asks the agent to save the already-open local Wikipedia pages \textit{Accessibility} and \textit{Computer accessibility} on the Chrome bookmark bar so they can be reopened without remembering or searching for them. \textbf{Construction and evaluation.} Setup opens two fixed Kiwix pages hosted inside the benchmark environment. The evaluator inspects Chrome's structured bookmark state and requires both exact local URLs on the bookmark bar.
